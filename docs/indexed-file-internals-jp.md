# PowerRustCOBOL 索引ファイルの内部構造(`PRCIDXD1` ページ方式エンジン)

本書は、`STORAGE IS DISK`(既定値)を指定して宣言された
`ORGANIZATION IS INDEXED` ファイルを支える、**永続的かつページ方式のディスク上**
エンジンの概念スキーマです。B+木とスロット式ページによる設計で、レコードを要求
に応じて読み込むため、ファイルの大きさにかかわらず RAM 使用量は一定の範囲に
収まります。

> **範囲。** 本書が説明するのは*物理エンジン*(`DiskIndexedFile`、コンテナ
> マジック `PRCIDXD1`)です。これは
> [`indexed-file-format-en.md`](indexed-file-format-jp.md) に記述された、単一ブロブで
> 自己記述型の `PRCIDX1` コンテナとは別の成果物であり、そちらは将来の富士通
> インポータが必要とするメタデータをモデル化しています。インメモリエンジン
> (`STORAGE IS MEMORY`、`IndexedFile`)は同じ論理モデルの簡略版です
> (ディスク上の B+木ではなく BTreeMaps を使用)。
>
> **クラッシュ耐性を持つ** 2 つ目の `STORAGE IS DISK` エンジン(オプトイン、
> 純 Rust の redb ACID ストア上に構築)は、本エンジンの RAM 依存ディレクトリと
> CLOSE 時のみの永続化という制約を解消します —
> [`indexed-redb-engine-jp.md`](indexed-redb-engine-jp.md) を参照してください。

実装:
[`crates/cobolt-runtime/src/indexed_disk.rs`](../crates/cobolt-runtime/src/indexed_disk.rs)、
レコードの(非)実体化は
[`crates/cobolt-runtime/src/files.rs`](../crates/cobolt-runtime/src/files.rs)。

---

## 1. 設計を一文で

**1 枚のヘッダーページ + N 本の B+木(キーごとに 1 本)→ RecordId ディレクトリ →
位置ベースで固定幅のレコードイメージを収めたスロット式データページ** から成る
ページ方式のファイルであり、フリーリスト、オーバーフローチェーン、任意の RLE
圧縮、そしてトランザクション用の実行中アンドゥログを備えます。

---

## 2. ファイルは固定 4 KiB ページの配列

```
 バイト 0                                                     ファイル終端
 ┌────────┬────────┬────────┬────────┬────────┬────────┬───── ... ─────┐
 │ Page 0 │ Page 1 │ Page 2 │ Page 3 │ Page 4 │ Page 5 │     ...       │
 │ HEADER │ B+tree │ B+tree │  DATA  │ DATA   │  DIR   │               │
 └────────┴────────┴────────┴────────┴────────┴────────┴───────────────┘
   PAGE_SIZE = 4096 バイト(固定)。   ページ ID = バイトオフセット / 4096。
```

ページ 0 **より後ろ**のすべてのページは、先頭バイト(ページ種別タグ)によって
自分自身を識別します。解放されたページはフリーリストを通じて再利用されるため、
ディスク上の物理的なページ順序はレコードの論理順序を **たどりません**。

| タグ | 定数          | ページが保持するもの                              |
|-----|---------------|--------------------------------------------------------|
| `1` | `PT_INTERNAL` | B+木の内部(ルーティング)ノード                        |
| `2` | `PT_LEAF`     | B+木のリーフノード(兄弟と双方向リンク)                |
| `3` | `PT_DATA`     | 複数のレコードイメージを詰め込むスロット式ページ         |
| `4` | `PT_OVERFLOW` | インラインに収まりきらない大きなレコードの継続部分       |
| `5` | `PT_DIR`      | RecordId ディレクトリの一部分                           |

---

## 3. ページ 0 — ヘッダー

ページ 0 は*スキーマ*が格納される唯一の場所であり、一度だけ書き込まれます。
フィールドはリトルエンディアンで、次の順に並びます。

```
 PRCIDXD1   version  page_size  rec_fmt  compressing  record_len
 (8 バイト) (u16)    (u32)      (u8 = 1) (u8 0/1)     (u32)
 ──────────────────────────────────────────────────────────────────────
 next_page_id   free_list_head   record_count   data_tail      (各 u64)
 primary_root   dir_head         directory_len                 (各 u64)
 ──────────────────────────────────────────────────────────────────────
 alt_root_count (u16) → [ alt_root : u64 ] × N     (代替キーごとに B+木ルート 1 本)
 ──────────────────────────────────────────────────────────────────────
 キースキーマ:  key_count (u16) → キーごとに(まずプライマリ、次に代替):
     duplicates_allowed (u8)
     part_count (u16) → [ offset:u32, length:u32 ] × パーツ数   (複合キーのパーツ)
```

| ヘッダーフィールド | 意味                                                  |
|-------------------|---------------------------------------------------------|
| `version`         | 形式バージョン(現在は `1`)。                           |
| `page_size`       | ページサイズ(バイト単位、4096)。                       |
| `rec_fmt`         | レコード形式: `1` = 固定長。                            |
| `compressing`     | ディスク上でレコードのペイロードを RLE 圧縮する場合 `1`。 |
| `record_len`      | 論理的な(非圧縮の)レコード長(バイト)。               |
| `next_page_id`    | フリーリストが空のときに次に割り当てるページ ID。       |
| `free_list_head`  | 回収済みページのフリーリストの先頭ページ(`0` = なし)。 |
| `record_count`    | 生存しているレコードの数。                              |
| `data_tail`       | インライン書き込みを受け付けている現在の `PT_DATA` ページ(`0` = なし)。 |
| `primary_root`    | プライマリキーの B+木のルートページ。                   |
| `dir_head`        | RecordId ディレクトリの最初の `PT_DIR` ページ(`0` = なし)。 |
| `directory_len`   | ディレクトリのエントリ数(これまでに割り当てた RecordId の総数)。 |
| `alt_root[k]`     | 代替キー *k* の B+木のルートページ。                    |
| キースキーマ       | キーごとの重複ポリシー + 複合パーツのバイト範囲。        |

**ヘッダーに意図的に*含めていない*もの:** **データフィールド名**も
**レコード単位のメタデータ**も存在しません。スキーマは純粋に*キーのジオメトリ*
(バイト範囲)だけです。レコードに関するそれ以外のすべては位置で決まります —
§6 を参照。

## 4. アクセス経路(キー指定の `READ` はどう解決されるか)

```
  COBOL のキー値(バイト列)
        │
        ▼
  ┌──────────────┐   primary_root(RECORD KEY によるランダム READ)または
  │  B+tree      │   alt_roots[k](READ KEY IS <alt>)から開始。内部ノードが
  │  (キーごと)  │   キーで経路を決め、リーフが (key_bytes → RecordId) を保持し、
  │              │   READ NEXT / READ PREVIOUS / START のために双方向
  └──────┬───────┘   (next/prev)にリンクされている。
         │  RecordId(物理位置に依存しない安定した整数)
         ▼
  ┌──────────────┐   directory[RecordId] = RecLoc { kind, page, slot, len }
  │  RecordId    │     kind: 0 = 空き/墓標、1 = インライン、2 = オーバーフロー先頭
  │ ディレクトリ │     len : 格納された(圧縮されている場合もある)バイト長
  └──────┬───────┘
         │  (page, slot)
         ▼
  ┌──────────────┐   スロット式 DATA ページ → スロットディレクトリ →
  │ DATA ページ  │   (offset, len) → 生のレコードイメージ(`compressing` なら
  └──────┬───────┘   展開される)。
         ▼
  固定幅のレコードバイト列
        │  RecordLayout.distribute()
        ▼
  作業メモリ上の FD の基本項目へ分配される
```

**1 レコード、多数のキー。** プライマリキーもすべての代替キーも*同じ* RecordId
を指すため、各レコードの格納コピーはちょうど 1 つだけです。代替インデックスは、
共有された RecordId ディレクトリの上に重ねられた追加の B+木にすぎません。代替値
の重複は、そのキーが `WITH DUPLICATES` と宣言されている場合に許されます。

## 5. ページの内部

### 5.1 B+木ノード(`PT_INTERNAL` / `PT_LEAF`)

ノードは操作のためにメモリへ読み込まれ、変更され、必要なら分割され、書き戻され
ます。

```
 リーフ:    type=2 | next:u64 | prev:u64 | count:u16 | [ klen:u16, key, RecordId:u64 ] × count
 内部:      type=1 | child0:u64           | count:u16 | [ klen:u16, key, child:u64  ] × count
```

- リーフは **双方向にリンク**(`next`/`prev`)されているため、`START` の後の順序
  走査は兄弟を直接たどります — これが RustCOBOL の昇順キー `READ NEXT` です。
- 挿入は、直列化したノードが `PAGE_SIZE` を超える場合に **あふれて分割** され、
  中央値のキーが親へ昇格します。
- 内部ノードは `child0` と *(区切りキー, 子)* の組を保持します。

### 5.2 スロット式データページ(`PT_DATA`)

```
 ┌─ バイト 0┬─ 1..3 ──┬─ 3..5 ──┬─ スロット一覧 ────────┬─ 空き ─┬─ レコード ────┐
 │ type=3   │ slot_   │ free_   │ (off:u16, len:u16) ×N │        │  詰め込み     │
 │          │ count   │ top     │ 増加  →               │        │  ←  増加      │
 └──────────┴─────────┴─────────┴───────────────────────┴────────┴───────────────┘
```

- 5 バイトのページヘッダーに続いて、前方から伸びる **スロットディレクトリ** が
  あり、**レコードのペイロード** は後方から伸びます。2 つの領域が出会うまでは、
  レコードはインラインに収まります。
- スロットは `(offset, len)` です。レコードを削除すると、そのスロットの
  `len = 0`(墓標)になります。ページ上のすべてのスロットが空きになると、ページ
  全体がフリーリストへ返却されます。
- `RecLoc` の `slot` フィールドは、このスロットディレクトリの添字です。

### 5.3 オーバーフローチェーン(`PT_OVERFLOW`)

インライン上限(`PAGE_SIZE − ヘッダー − スロット 1 個`)より大きなレコードは、
オーバーフローページの連結チェーンとして格納されます。その `RecLoc.kind = 2` と
なり、`page` はチェーンの先頭を指します。

### 5.4 RecordId ディレクトリ(`PT_DIR`)

```
 directory[RecordId]  →  RecLoc { kind:u8, page:u64, slot:u16, len:u32 }   (1 エントリ 15 バイト)
```

ディレクトリは、ファイルが開いている間は `Vec<RecLoc>` として RAM 上に保持され
(そのため RecordId の参照は O(1) の添字アクセスです)、クローズ時に
`PT_DIR` ページの連鎖(`dir_head` から開始)として永続化されます。B+木が格納
するのは RecordId であって物理アドレスではないため、どのインデックスにも触れず
にレコードをディスク上で移動できます。

## 6. レコードイメージそのもの(位置ベース、名前なし)

ディスク上のレコードは、フィールドの*オフセット*で配置された単一の
**固定幅バイトバッファ**です。ペイロードの中にフィールド名もタグも区切り文字も
ありません。次の定義の場合:

```cobol
01 CUST.
   05 CUST-ID    PIC 9(5).
   05 CUST-NAME  PIC X(10).
   05 CUST-CITY  PIC X(8).
```

格納されるイメージは 23 バイトになります。

```
 オフセット:  0        5                     15              23
              ┌────────┬─────────────────────┬───────────────┐
 ペイロード:  │ 00001  │ John Doe░░          │ Sao Paulo     │
              └────────┴─────────────────────┴───────────────┘
                ID(5)     NAME(10)              CITY(8)
                (░ = 空白によるパディング)
```

- `RecordLayout::materialize()` は `WRITE`/`REWRITE` のために FD の基本項目を
  オフセット順にこのバッファへ詰め込み、`RecordLayout::distribute()` は `READ`
  でその逆を行います。フィールド → オフセットの対応表はプログラムの
  `RecordLayout`(`FD` から導出)の中にだけ存在し、ファイルの中には **決して**
  ありません。
- **同一性は位置である。** これは「レコードごとにキーを繰り返さない」という考え
  方の極限です。フィールドの同一性はレコードあたり *0* バイトのコストで、
  フィールドアクセスは事前計算されたオフセットによる O(1)(解析処理なし)です。
  キー以外のフィールド名を変更してもディスク上は何も変わりません。キーフィールド
  名の変更で書き換わるのはヘッダーのキースキーマだけで、レコードもインデックスも
  そのままです。フィールドのオフセットや幅の変更だけが、データの書き直しを必要と
  する唯一の変更です — これは固定長レコード(および実際の ISAM/VSAM)に本質的な
  性質です。

### 圧縮

`STORAGE IS DISK WITH COMPRESSION` を指定すると、**格納される** ペイロードは
PackBits-RLE で圧縮され(`compress.rs`)、`RecLoc.len` は*格納された*長さになり
ます。バッファは読み取り時に `record_len` へ戻されます。圧縮はキーのジオメトリ
にもアクセス経路にも影響しません。

## 7. 空き領域と再利用

- **フリーリスト。** `free_list_head` は、空になったデータページや分割で孤立した
  ノードなどから回収したページを連鎖させます。`allocate` は `next_page_id` を
  増やす前にそこから取り出すため、領域は再利用され、ファイルは単調には増えません。
- **墓標。** `DELETE` はスロットを(そして遅延的にデータページを)解放し、
  ディレクトリのエントリを `RecLoc::FREE` と印付けます。その RecordId は引退し
  ます。

## 8. トランザクション(実行中のアンドゥログ)

ディスクエンジンは、直前の `COMMIT`/`OPEN` 以降のすべての変更について、その逆
操作を記録した **アンドゥログ** を保持します。

```
 DiskUndo::Insert(key)        ← WRITE   → そのキーを削除して取り消す
 DiskUndo::Update(prev_image) ← REWRITE → 直前のイメージを書き戻して取り消す
 DiskUndo::Delete(prev_image) ← DELETE  → イメージを書き戻して取り消す
```

- `OPEN` はトランザクションを開始し(ログを消去)、`COMMIT` は変更を永続化して
  新しいトランザクションを開始し、`ROLLBACK` は逆操作を逆順に再生し、`CLOSE` は
  フラッシュします(暗黙のコミット)。`tx_replay` ガードによって、逆操作自身が
  再びログに記録されることはありません。
- これは **プログラムレベル** のロールバックです。永続的な先行書き込みログによる
  クラッシュ復旧は今後の課題です。COBOL の `COMMIT`/`ROLLBACK` 動詞については
  言語リファレンスを参照してください。これらの動詞が作用するのは
  **INDEXED ファイル** であって、SQL 接続ではない点に注意してください。

## 9. OPEN 時の検証

`OPEN` 時に、ヘッダーに格納されたキースキーマがプログラムの `SELECT`(レコード
長、キーの数、各キーのパーツと重複ポリシー)と照合されます。不一致の場合は
COBOL ファイル状態 `39` を返します。存在しないファイルを `INPUT` で開いた場合は
`35`、壊れているか短すぎるヘッダーの場合は `90` を返します。(厳格な検証は
エンジンの `strict_metadata` フラグで緩められます。)

## 10. クイックリファレンス — 何がどこに保存されるか

| 対象                            | 保存場所                                | コピー数     |
|-------------------------------|----------------------------------------|-------------|
| キーのジオメトリ(オフセット/幅) | ヘッダー(ページ 0)のキースキーマ      | 1 回        |
| データフィールド名             | プログラムの `FD` のみ                  | ファイル内には無し |
| レコードのバイト列             | `PT_DATA` / `PT_OVERFLOW` ページ        | 1/レコード  |
| キー → RecordId               | キーごとに 1 本の B+木                  | 1/キー      |
| RecordId → 物理位置           | RecordId ディレクトリ(`PT_DIR` 連鎖)  | 1/レコード  |
| 空きページ                     | フリーリスト(`free_list_head`)        | —           |
| 未コミット変更の逆操作          | RAM 上のアンドゥログ                    | トランザクションごと |
```

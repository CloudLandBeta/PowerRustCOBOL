# ベンチマーク

1.37.0 のベースライン。負荷がかかったときにランタイムがどれだけ速いか、そして
そこへ到達するためにアロケータへどれだけ負担をかけているかを示します。

```sh
cargo run --release -p cobolt-bench              # すべて
cargo run --release -p cobolt-bench -- dispatch  # 部分文字列で 1 つのワークロードだけ
PRC_BENCH_SCALE=0.05 cargo run --release -p cobolt-bench   # 20 分の 1。手早く確認したいとき
```

`--release` は省略できません。デバッグビルドは最適化が「ない」状態を測るだけで
あり、ハーネスはその数値が引用されてしまわないよう、ヘッダーにその旨を明示し
ます。

## 何を測っているか

COBOL のワークロードはいずれも、**出荷されるバイナリがたどるのと同じ経路**を
通ります。すなわち、トークン化、構文解析、意味解析、`Interpreter::run` です。
`rcrun build` が生成する `main.rs` が、埋め込まれた AST に対して行うのがまさに
これだからです。同一プロセス内で実行することがアロケータのカウンタを可能にして
います。つまりこの数値は、あなたが引き渡すすべてのバイナリの内部にあるインタプ
リタそのものを表しています。

メモリは常駐セットの推移ではなく、アロケーションの挙動として報告します。Rust に
ガベージコレクタはないため測るべきポーズは存在せず、負荷時に問題になるのは
**回転量**です。すなわち、ワークロードがアロケータに入る回数、通過するバイト数、
そしてピーク時に生存している量です。カウント機能付きのグローバルアロケータ
([`counting_alloc.rs`](../crates/cobolt-bench/src/counting_alloc.rs)) が、外部
プロファイラなしに 3 プラットフォームすべてでこの 3 つを正確に提供します。

意図的に測っていないものが 2 つあります。プロセスの起動時間とバイナリサイズで
す。これらは `rcrun build` が生成した実物の成果物で測定してください。

## ベースラインが語ること

**ボトルネックはツリー走査ではなくアロケータです。** 毎秒 570 万文という
ディスパッチ速度は立派ですが、そこへ到達するのに **600 万文に対して 2,400 万回
のアロケーション**を要しました。2 つの `COMP` 項目に対する `ADD 1 TO ACC` は、
本来ヒープに一切触れないはずなのに、アロケータを 4 回通ります。これは最適化の
方針を変えます。最初に効くのは値システムとオペランド経路であって、ツリー走査型
インタプリタをバイトコード VM に置き換えることではありません。VM はディスパッチ
を安くする一方で、1 文あたり 4 回のアロケーションには手を触れないからです。

**段落呼び出しは不釣り合いに高くつきます。** `PERFORM <paragraph>` 1 回あたり
18 回のアロケーションと約 820 バイト。インライン 1 文あたり 4 回と比べてくださ
い。50 万回の呼び出しで 410 MB が回転します。呼び出し経路が毎回何を組み立てて
いるにせよ、それが表の中で最も密度の高い標的です。

**英数字レコードは想定どおりフィールド単位でアロケートします。** 4 フィールドの
行を読み書きしてレコードあたり 65 回というのは、`CobolValue::String` がフィール
ドごとに `Vec<u8>` を保持し、さらに `MOVE` のたびに新しく確保しているというこ
とです。短い文字列のインライン表現、あるいはレコード自身のバッファへのスライス
であれば、ここに即座に表れるはずです。

**オブジェクトのプロパティ読み出しは理由なくアロケートします。** 24 回のプロパ
ティ読み出しでオブジェクトあたり 55 回。`CoboltObject::get_property`、
`get_str`、`get_bool`、`get_i64` はいずれも `name.to_ascii_uppercase()` を呼び
出します。検索を大文字小文字非依存にするためだけに、**読み出しごとに** `String`
を 1 つ確保して捨てているのです。大文字小文字を区別しないキーのラッパーを使え
ば、この列はまるごと消えます。

**INDEXED エンジンは問題ではありません。** redb はレコードあたり 0.66 回のアロ
ケーションで毎秒 141k レコードを挿入し、ほぼアロケーションなしで毎秒 150 万回の
ランダム読み出しをこなします。ストレージは、それを供給するインタプリタより
十分に先を行っています。

期待できる効果の順に並べると、ベースラインが示す最適化の順序は、1 文あたりの
アロケーション、次に段落呼び出し経路、次に英数字向けの `CobolValue`、そして
オブジェクトプロパティの大文字化です。ストレージはそれらよりずっと下まで登場し
ません。

## ワークロード

| ワークロード | 何を切り出すか |
|---|---|
| `dispatch (PERFORM VARYING)` | ツリー走査のオーバーヘッド。ループ判定、増分、1 文、その下の作業は最小限 |
| `dispatch (PERFORM paragraph)` | 段落呼び出しのオーバーヘッド。上のインラインの場合との対比 |
| `decimal COMPUTE` | `CobolNumeric` の i128 スケール演算 — COBOL の金額計算 |
| `record batch` | 英数字フィールドを持つ 1000 行のテーブルの書き込みと読み戻し。バッチ負荷下の値システム |
| `object churn` | `ObjectRegistry` の生成・読み出し・破棄 — コントロールの多い form にかかるコスト |
| `indexed redb` | INDEXED ファイルエンジン。一括挿入のあとランダムキー読み出し |

`indexed redb` の 2 行は、`cobolt-runtime::indexed_redb` の内部に `#[ignore]`
付きで眠っていたマイクロベンチマーク `open_table_cost` を復活させ、一般化したも
のです。正確な `--ignored` の指定を誰かが思い出したときにしか動かなかったため、
このエンジンには常設のベースラインがありませんでした。いまはあります。元の結論
はそのまま維持しています。すなわち、テーブルハンドルは書き込みトランザクション
全体で一度だけ開かれ、それは挿入ごとに 2 回開く場合より約 16 % 高速でした。

## ワークロードを追加する

[`crates/cobolt-bench/src/main.rs`](../crates/cobolt-bench/src/main.rs) に
`measure(name, unit, || { ...; ops_performed })` を返す `bench_*` 関数を追加し、
`main` の中で `wanted(...)` フィルタの背後に登録してください。カウンタはクロー
ジャを自動的に包みます。返す値は反復回数ではなく*仕事*の単位数にしてください。
そうすれば `ops/sec` と `allocs/op` がワークロード間で比較可能なまま保たれます。

新しいワークロードは決定的に保ってください。ランダム読み出しのプローブが乱数生
成器ではなく固定の乗算ステップを使っているのは、まさにこのためです。実行のたび
に並びが変わるベンチマークは、昨日の数値と比較できません。

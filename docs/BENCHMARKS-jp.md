# ベンチマーク

1.37.0 のベースライン — 負荷がかかったときにランタイムがどれだけ速く動き、そこに
到達するためにアロケーターにどれだけ依存しているか。

```sh
cargo run --release -p cobolt-bench              # すべて
cargo run --release -p cobolt-bench -- dispatch  # 部分文字列で 1 つの処理だけ
PRC_BENCH_SCALE=0.05 cargo run --release -p cobolt-bench   # 20 分の 1 の規模で手早く確認
```

`--release` は省略できません。デバッグビルドは最適化の「不在」を測っているだけで
あり、ハーネスはその数値が引用されないようヘッダーにその旨を明示します。

## 何を測っているか

COBOL の各ワークロードは、**出荷されるバイナリとまったく同じ経路**をたどります。
トークン化、構文解析、意味解析、`Interpreter::run` — これは `rcrun build` が生成
する `main.rs` が、埋め込まれた AST に対して行うことそのものです。プロセス内で
実行することがアロケーターのカウンターを可能にします。つまりここでの数値は、
あなたが引き渡すすべてのバイナリの内部にあるインタープリターを表しています。

メモリは常駐セットの推移ではなく、アロケーションの挙動として報告します。Rust に
ガベージコレクターはないため測るべき停止時間は存在しません。負荷時に重要なのは
**回転量** — ワークロードがアロケーターに入る回数、通過するバイト数、ピーク時に
生存している量です。カウント機能付きのグローバルアロケーター
([`counting_alloc.rs`](../crates/cobolt-bench/src/counting_alloc.rs)) が、外部
プロファイラーなしで、3 つのプラットフォームすべてでこの 3 つを正確に提供します。

意図的に**測っていない**ものが 2 つあります。プロセスの起動時間とバイナリサイズ
です。それらは `rcrun build` が生成する実物の成果物で測定してください。

## ベースラインが示していること

**ボトルネックはツリー走査ではなくアロケーターです。** 毎秒 570 万文というディス
パッチ速度は立派ですが、そこに届くまでに **600 万文に対して 2,400 万回のアロ
ケーション**を要しました。2 つの `COMP` 項目に対する `ADD 1 TO ACC` は、本来
ヒープに触れる必要がまったくないのに、アロケーターを 4 回通過します。これは最適化
の方針を組み替えます。最初に効くのは値システムとオペランド経路であって、ツリー
walk インタープリターをバイトコード VM に置き換えることではありません。VM は
ディスパッチを安くしますが、1 文あたり 4 回のアロケーションはそのまま残ります。

**段落呼び出しは不釣り合いに高価です。** `PERFORM <paragraph>` 1 回あたり 18 回の
アロケーションと約 820 バイト。インライン文 1 つあたり 4 回と比べてください。
50 万回の呼び出しで 410 MB が回転します。呼び出し経路が 1 回ごとに構築している
ものが何であれ、それが表の中で最も密度の高い標的です。

**英数字レコードは想定どおり項目ごとにアロケートします。** 4 項目の行を 1 件
読み書きするのにレコードあたり 65 回というのは、項目ごとに `Vec<u8>` を所有する
`CobolValue::String` に加え、`MOVE` のたびに新しいものが生まれるためです。短い
文字列のインライン表現、あるいはレコード自身のバッファーへのスライスを導入すれ
ば、ここに即座に表れます。

**オブジェクトのプロパティ読み取りは理由もなくアロケートしています。** プロパティ
を 24 回読むあいだにオブジェクトあたり 55 回。`CoboltObject::get_property`、
`get_str`、`get_bool`、`get_i64` はいずれも `name.to_ascii_uppercase()` を呼びま
す。検索を大文字小文字の区別なしにするためだけに、**読み取りごとに** `String` が
1 つ確保されて捨てられているのです。大文字小文字を区別しないキーのラッパーを使え
ば、この列は丸ごと消えます。

**INDEXED エンジンは問題ではありません。** redb は 1 レコードあたり 0.66 回のアロ
ケーションで毎秒 14.1 万レコードを挿入し、ほとんどアロケーションなしで毎秒 150 万
回のランダム読み取りを処理します。ストレージは、それを supply するインタープリタ
ーより十分に先を行っています。

期待できる効果の順に並べると、ベースラインが示す最適化の順序は、1 文あたりの
アロケーション、次に段落呼び出しの経路、次に英数字向けの `CobolValue`、そして
オブジェクトプロパティの大文字化です。ストレージはそれらよりはるかに下にしか
現れません。

## ワークロード

| ワークロード | 何を切り出しているか |
|---|---|
| `dispatch (PERFORM VARYING)` | ツリー走査のオーバーヘッド — ループ判定、インクリメント、1 文、その下の処理は最小限 |
| `dispatch (PERFORM paragraph)` | 段落呼び出しのオーバーヘッド。上のインライン事例との対比 |
| `decimal COMPUTE` | `CobolNumeric` の i128 スケール演算 — COBOL の金額計算 |
| `record batch` | 英数字項目を持つ 1000 行のテーブルの書き込みと読み戻し。バッチ負荷下の値システム |
| `object churn` | `ObjectRegistry` の生成/読み取り/破棄 — コントロールの多いフォームの費用 |
| `indexed redb` | INDEXED ファイルエンジン — 一括挿入、続いてランダムキー読み取り |

`indexed redb` の 2 行は、`cobolt-runtime::indexed_redb`
(`indexed_redb.rs:1264`) の中に今も `#[ignore]` 付きで置かれているマイクロ
ベンチマーク `open_table_cost` を、取り戻して一般化したものです。あれは誰かが
正確な `--ignored` の呼び出しを覚えていたときにしか動かず、エンジンには常設の
ベースラインがありませんでした。いまはここにあり、元のものはそのまま残してあり
ます。元の結論も維持しています — テーブルハンドルは書き込みトランザクション全体
で一度だけ開かれ、挿入ごとに 2 回開く場合より約 16 % 高速でした。

## ワークロードを追加する

[`crates/cobolt-bench/src/main.rs`](../crates/cobolt-bench/src/main.rs) に
`measure(name, unit, || { ...; ops_performed })` を返す `bench_*` 関数を追加し、
`main` の中で `wanted(...)` フィルターの後ろに登録してください。カウンターは
クロージャーを自動的に包みます。返すのは反復回数ではなく*仕事*の単位数にしてく
ださい。そうすれば `ops/sec` と `allocs/op` がワークロード間で比較可能なまま保た
れます。

新しいワークロードは決定的に保ってください。ランダム読み取りのプローブが乱数生成
器ではなく固定の乗算ステップを使っているのは、まさにこのためです。実行のたびに
並びが変わるベンチマークは、昨日の数字と比較できません。

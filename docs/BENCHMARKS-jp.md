# ベンチマーク

1.37.0 のベースライン。負荷の下でランタイムがどれだけ速いか、そしてそこに至る
までにアロケータへどれだけ寄りかかっているか。

```sh
cargo run --release -p cobolt-bench              # everything
cargo run --release -p cobolt-bench -- dispatch  # one workload, by substring
PRC_BENCH_SCALE=0.05 cargo run --release -p cobolt-bench   # a twentieth, for a quick check
```

`--release` は省略できません。debug ビルドは最適化の*不在*を測ってしまうため、
ハーネスはその旨をヘッダに明示し、数値がそのまま引用されないようにしています。

## 何を測っているか

すべての COBOL ワークロードは、**出荷されたバイナリがたどるのと同じ経路**を
通ります — トークナイズ、構文解析、意味解析、`Interpreter::run`。`rcrun build`
が生成する `main.rs` が、埋め込んだ AST に対して行うのがまさにこれだからです。
同一プロセス内で実行することがアロケータのカウンタを可能にしています。つまり
これらの数値は、あなたが手渡すすべてのバイナリの中にいるインタプリタそのものを
表しています。

メモリは resident set の曲線ではなく、アロケーションの挙動として報告します。
Rust にガベージコレクタはないので測るべき停止時間はありません。負荷の下で重要
なのは**回転量**です — ワークロードがアロケータに入る回数、通過するバイト数、
そしてピーク時に生存している量。カウンタ付きのグローバルアロケータ
([`counting_alloc.rs`](../crates/cobolt-bench/src/counting_alloc.rs)) が、外部
プロファイラなしに、3 つのプラットフォームすべてでこの 3 つを正確に供給します。

これが意図的に**測らない**もの: プロセスの起動時間とバイナリサイズ。この 2 つは
`rcrun build` が生成した実物の成果物で測ってください。

## ベースラインが語ること

**ボトルネックは木の走査ではなくアロケータです。** 毎秒 570 万文という
ディスパッチ速度は立派ですが、そこに到達するのに**600 万文に対して 2400 万回の
アロケーション**を要しました。`COMP` 同士の `ADD 1 TO ACC` は本来ヒープに一切
触れないはずなのに、アロケータへの往復が 4 回かかっています。これは最適化の
方針を組み替えます。最初に効くのは値システムとオペランド経路であって、木を
走査するインタプリタをバイトコード VM に置き換えることではありません。VM は
ディスパッチを安くする一方、1 文あたり 4 回のアロケーションには手を触れません。

**段落呼び出しは不釣り合いに高価です。** `PERFORM <paragraph>` 1 回あたり 18
アロケーション・約 820 バイト。インライン 1 文あたり 4 回に対してこれです。
50 万回の呼び出しで 410 MB が回転します。呼び出し経路が毎回何を組み立てている
にせよ、表の中で最も密度の高い標的です。

**英数字レコードは想定どおりフィールドごとにアロケートします。** 4 フィールドの
行を読み書きしてレコードあたり 65 アロケーションというのは、`CobolValue::String`
がフィールドごとに `Vec<u8>` を所有し、さらに `MOVE` のたびに新しく確保している
ということです。短い文字列のインライン表現、あるいはレコード自身のバッファを
スライスする方式にすれば、ここに即座に表れます。

**オブジェクトのプロパティ読み出しは理由もなくアロケートします。** 24 回の
プロパティ読み出しでオブジェクトあたり 55 アロケーション。
`CoboltObject::get_property`、`get_str`、`get_bool`、`get_i64` がそれぞれ
`name.to_ascii_uppercase()` を呼んでおり、検索を大文字小文字の区別なしにする
ためだけに、**読み出しごとに** `String` を 1 つ確保しては捨てています。大文字
小文字を無視するキーのラッパーを入れれば、この列はまるごと消えます。

**INDEXED エンジンは問題ではありません。** redb はレコードあたり 0.66
アロケーションで毎秒 14.1 万レコードを挿入し、ほぼゼロアロケーションで毎秒
150 万件のランダム読み出しをさばきます。ストレージは、それを養うインタプリタ
よりも余裕をもって先を走っています。

期待効果の順に並べると、ベースラインが示す最適化の順序は、1 文あたりの
アロケーション、次に段落呼び出しの経路、次に英数字向けの `CobolValue`、次に
オブジェクトプロパティの大文字化です。ストレージが登場するのは、それらより
ずっと下です。

## ワークロード

| ワークロード | 何を切り出すか |
|---|---|
| `dispatch (PERFORM VARYING)` | 木の走査そのもののコスト: ループ判定、加算、1 文、その下はごく軽い処理 |
| `dispatch (PERFORM paragraph)` | 段落呼び出しのコストを、上のインラインの場合と対比する |
| `decimal COMPUTE` | `CobolNumeric` の i128 スケール演算 — COBOL の金額計算 |
| `record batch` | 英数字フィールドを持つ 1000 行の表を書き込み、読み戻す。バッチ負荷下の値システム |
| `object churn` | `ObjectRegistry` の生成・読み出し・破棄 — 多数のコントロールを持つフォームの費用 |
| `indexed redb` | INDEXED ファイルエンジン: 一括挿入、その後ランダムキー読み出し |

`indexed redb` の 2 行は、`cobolt-runtime::indexed_redb` の中で `#[ignore]` を
付けられて眠っていたマイクロベンチマーク `open_table_cost` を復活させ、一般化
したものです。誰かが正確な `--ignored` 呼び出しを覚えていたときにしか走らな
かったため、このエンジンには常設のベースラインがありませんでした。今はあります。
元の結論はそのまま保たれています — テーブルハンドルは書き込みトランザクション
全体で 1 回だけ開かれ、挿入ごとに 2 回開く場合よりおよそ 16 % 速いと計測され
ました。

## ワークロードを追加する

[`crates/cobolt-bench/src/main.rs`](../crates/cobolt-bench/src/main.rs) に
`measure(name, unit, || { ...; ops_performed })` を返す `bench_*` 関数を追加し、
`main` の中で `wanted(...)` フィルタの後ろに登録します。カウンタはクロージャを
自動的に包みます。返す数は反復回数ではなく*仕事*の単位数にしてください。そう
すれば `ops/sec` と `allocs/op` がワークロード間で比較可能なままになります。

新しいワークロードは決定的に保ってください。ランダム読み出しのプローブが乱数
生成器ではなく固定の乗算ステップを使っているのは、まさにこのためです。実行の
たびに並びが変わるベンチマークは、昨日の数値と比較できません。

# 基准测试

1.37.0 基线：运行时在负载下有多快，以及为达到这一速度它对分配器的依赖有多重。

```sh
cargo run --release -p cobolt-bench              # 全部
cargo run --release -p cobolt-bench -- dispatch  # 按子串运行单个负载
PRC_BENCH_SCALE=0.05 cargo run --release -p cobolt-bench   # 二十分之一规模，用于快速检查
```

`--release` 不是可选项。调试构建测量的是"没有优化"这件事本身，因此测试框架会在其
表头中说明，而不是任由这些数字被引用。

## 测量什么

每个 COBOL 负载都走**与交付二进制文件完全相同的路径**——分词、语法分析、语义分析、
`Interpreter::run`——因为这正是 `rcrun build` 生成的 `main.rs` 对其内嵌 AST 所做的
事情。在进程内运行使分配器计数成为可能：这些数字描述的正是你交付的每个二进制文件
内部的那个解释器。

内存以分配行为报告，而不是常驻集曲线。Rust 没有垃圾回收器，因此没有暂停可测；负载
下真正重要的是**周转量**——一个负载进入分配器多少次、多少字节流经它、峰值时有多少
存活。一个带计数的全局分配器
([`counting_alloc.rs`](../crates/cobolt-bench/src/counting_alloc.rs)) 在三个平台上
都能精确提供这三项，且不需要任何外部性能分析器。

有两件事是刻意**不**测量的：进程启动时间和二进制文件体积。请在 `rcrun build` 产出
的真实成品上测量这两项。

## 1.37.0 基线

Apple M3 Pro，18 GB，macOS 15.5，rustc 1.95.0，release 配置，2026-07-27。

关注的那一列。

| 负载 | 操作数 | 耗时 | 操作/秒 | 分配次数 | 每次操作 | 周转 MB | 峰值存活 MB |
|---|---:|---:|---:|---:|---:|---:|---:|
| dispatch (PERFORM VARYING) | 6,000,000 语句 | 1.049 秒 | 5,721,961 | 24,000,334 | 4.00 | 72.5 | 0.0 |
| dispatch (PERFORM paragraph) | 500,000 调用 | 0.729 秒 | 686,318 | 9,000,356 | 18.00 | 409.6 | 0.0 |
| decimal COMPUTE | 500,000 次计算 | 0.824 秒 | 606,461 | 10,000,499 | 20.00 | 41.0 | 0.0 |

| object churn (创建/读取/销毁) | 20,000 对象 | 0.092 秒 | 216,320 | 1,100,000 | 55.00 | 27.5 | 0.0 |
| indexed redb (批量插入) | 100,000 记录 | 0.710 秒 | 140,922 | 65,854 | 0.66 | 188.9 | 22.4 |
| indexed redb (随机读取) | 50,000 次读取 | 0.034 秒 | 1,489,965 | 9 | 0.00 | 0.0 | 22.4 |

## 基线说明了什么

**瓶颈是分配器，不是树遍历。** 每秒 570 万条语句的分派速率相当不错——但达到它付出了
**600 万条语句对应 2400 万次分配**的代价。对两个 `COMP` 字段执行 `ADD 1 TO ACC`
本不该碰堆，却要经过分配器四次。这重新界定了优化方向：最先见效的地方在值系统和
操作数路径，而不是把树遍历解释器换成字节码虚拟机。虚拟机会让分派更便宜，却会原封
不动地留下每条语句四次分配。

**段落调用的开销高得不成比例。** 每次 `PERFORM <paragraph>` 有 18 次分配、约 820
字节，而每条内联语句只有 4 次。五十万次调用周转 410 MB。调用路径每次调用构建的
东西——无论那是什么——都是表中密度最高的目标。

**字母数字记录按字段分配，这在预料之中。** 读写一个 4 字段的行、每条记录 65 次
分配，源于 `CobolValue::String` 为每个字段持有一个 `Vec<u8>`，再加上每次 `MOVE`
都会新建一个。采用内联的短字符串表示，或者直接切片到记录自身的缓冲区，都会立刻
在这里体现出来。

**对象属性读取毫无理由地进行分配。** 24 次属性读取中每个对象分配 55 次。
`CoboltObject::get_property`、`get_str`、`get_bool` 和 `get_i64` 都会调用
`name.to_ascii_uppercase()`——**每读一次**就分配并丢弃一个 `String`，仅仅为了让
查找不区分大小写。一个不区分大小写的键包装器可以整列消除这项开销。

**INDEXED 引擎不是问题所在。** redb 以每条记录 0.66 次分配的代价达到每秒 14.1 万条
记录的插入速度，并在几乎不分配的情况下提供每秒 150 万次随机读取。存储的速度远远
领先于向它供数的解释器。

按预期收益排序，基线给出的优化顺序是：每条语句的分配，然后是段落调用路径，然后是
用于字母数字的 `CobolValue`，最后是对象属性的大写转换。存储要排在这些之后很远的
位置才会出现。

## 负载

| 负载 | 它隔离了什么 |
|---|---|
| `dispatch (PERFORM VARYING)` | 树遍历开销：循环判断、自增、一条语句，下层工作极少 |
| `dispatch (PERFORM paragraph)` | 段落调用开销，与上面的内联情形对照 |
| `decimal COMPUTE` | `CobolNumeric` 的 i128 定标算术——COBOL 的货币运算 |
| `record batch` | 写入并读回含字母数字字段的 1000 行表；批量负载下的值系统 |
| `object churn` | `ObjectRegistry` 创建/读取/销毁——一个控件众多的窗体的代价 |
| `indexed redb` | INDEXED 文件引擎：批量插入，然后随机键读取 |

`indexed redb` 这两行，是把 `open_table_cost` 这个微基准恢复并推广后的版本；它至今
仍带着 `#[ignore]` 留在 `cobolt-runtime::indexed_redb`（`indexed_redb.rs:1264`）
里面。它只有在有人记得一条精确的 `--ignored` 调用时才会运行，因此该引擎一直没有
常设基线；现在这里有了，而原来的那个保持原位。它原本的结论也保留下来：表句柄在整个
写事务中只打开一次，实测比每次插入打开两次快约 16 %。

## 添加一个负载

在 [`crates/cobolt-bench/src/main.rs`](../crates/cobolt-bench/src/main.rs) 中添加
一个返回 `measure(name, unit, || { ...; ops_performed })` 的 `bench_*` 函数，并在
`main` 中注册到 `wanted(...)` 过滤器之后。计数器会自动包裹该闭包。请返回*工作*单位
的数量，而不是迭代次数，这样 `ops/sec` 和 `allocs/op` 才能在不同负载之间保持可比。

保持新负载的确定性。随机读取探针使用固定的乘法步长而不是随机数生成器，正是出于这个
原因：一个每次运行都重新洗牌的基准测试，无法与昨天的数字相比较。

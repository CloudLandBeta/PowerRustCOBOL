# WASM parity ledger — where a generated module and the interpreter differ

Every difference between the WebAssembly line (2.x.x) and the interpreter (1.x.x), with who is right. A difference that is the **interpreter's** defect is a fix for `main` (GOLDEN RULE #5) and is forward-ported; it is listed here until the operator decides. A difference that is deliberate stays here as the record of why.

| # | Construct | Module | Interpreter | Who is right | Status |
|---|---|---|---|---|---|

No NIST member exercises it. |
| 2 | `BLANK WHEN ZERO` numeric-edited item receiving a value that is zero only after truncation to the picture's decimals (`0.001` into `Z9.99`) | blanks | prints `0.00` (tests the value before truncation) | the module (the item's value is zero) | open, same fix as #1's family; no NIST member exercises it |

| 8 | `EXIT PROGRAM` / `GOBACK` inside a `PERFORM` in a called program | leaves the program and returns to the caller (COBOL-85 6.7.4) | carries on after the `PERFORM` | the module | open — report to the operator: a 1.x.x fix (found by `crates/cobolt-wasm/tests/calls.rs::a_callee_that_returns_from_inside_a_perform`); no NIST member exercises it |
| 9 | `CALL … RETURNING` with an identifier as the program name; `BY VALUE` | each callee returns to a block of its own that moves its RETURNING item; `BY VALUE` moves the value into a copy with the parameter's own USAGE and PICTURE (WASM-010 T13) | RETURNING works; `BY VALUE` of an item works; `BY VALUE` of a **literal** reaches the callee as zero (row 12) | the module | **closed** (2.0.35, `tests/parity_gaps.rs::returning_on_a_dynamic_call_and_by_value`) |

| 13 | A callee whose `RETURNING` item is in its LINKAGE SECTION | run-time error 1107 (a LINKAGE item the CALL did not pass): the module binds only `USING` parameters | not measured | — | **closed** (2.0.36, WASM-010 T20): the callee's LINKAGE `RETURNING` record is bound to storage of its own on every call; `tests/cobol/call/test-call-returning.cbl` now runs identically (`tests/corpus.rs`) |
| 14 | `BY REFERENCE` / `BY CONTENT` where the argument and the parameter are described differently (`PIC 9(4)` into `PIC S9(4) COMP`) | the parameter sees the argument's bytes (12336 for the text `0021`) | the parameter sees the value (21) | the module, by COBOL-85, which asks the two descriptions to agree; the interpreter keeps values, not bytes | by design (WASM-010 Q5, "answered, to confirm"): not a bug in either engine. Under the plan's working assumption Check would warn here; **no warning is emitted yet** — the `REDEFINES`/description warning (`WarningKind::RedefinesMayDiffer`) exists but has no difference to point at that is shown not to be a bug, so T13 emits none |
| 15 | `OPEN OUTPUT`, `I-O` or `EXTEND` of an INDEXED file declared `STORAGE IS MEMORY` **without** `WITH PERSISTENCE` | opens; the records live with the form instance until it closes (`cobolt_wasm_rt::idx`, WASM-010 T14). `WITH PERSISTENCE` is refused at build time: a browser module has no disk | status **37**: a memory file without `WITH PERSISTENCE` is a read-only copy (operator, 2026-10-01, `IndexedFile::open`) | neither is wrong: the desktop's rule protects data that looks saved and is not; a browser module saves nothing, and Q8 ("in-memory INDEXED files are in") and Q-new-1 (a `WRITE` the memory cannot hold is 89) only make sense if the file can be written | **working assumption, to confirm by the operator** (WASM-010 T14). | 16 | `SORT … USING`/`GIVING` on INDEXED (or any keyed) files; `MERGE` | refused at build time (`SORT` takes an `INPUT`/`OUTPUT PROCEDURE` in a browser module; `MERGE` reads files) | `SORT` reads and writes only sequential files (`read_all_records`/`write_all_records` see `OpenFile::Reader`/`Writer`): on an INDEXED file `USING` delivers no record and `GIVING` writes none, and the program is not told | the module refuses what it cannot do; the interpreter silently does nothing | open — the interpreter's silence is a 1.x.x matter (report to the operator); the module's refusal is by design |
| 17 | A `PIC N` (national) item in a group that travels as JSON | holds its text as UTF-8 bytes in its `2 × n` bytes, as every other routine of the module treats a national item (none converts to UTF-16); the limit is counted in UTF-16 units (S5), and a string whose UTF-8 bytes would not fit the `2 × n` bytes is refused `too-long` | the item holds characters; any string of at most `n` UTF-16 units is accepted | `cobolt-wire` (rule S5) | **open — generator gap**: a string of characters from U+0800 to U+FFFF (three UTF-8 bytes, one unit) filling more than two thirds of the item; the golden vectors do not reach it (WASM-010 T15). National items are bytes in the module everywhere, not only here |
| 18 | `COMPUTE r = a / 0 ON SIZE ERROR …` | the size error condition: the phrase runs, `r` is left as it was | the run stops with `RuntimeError::DivisionByZero` at the statement, the phrase notwithstanding (measured 2026-10-23; `DIVIDE … ON SIZE ERROR` by zero is handled on both) | the module (COBOL-85: a division by zero is a size error condition, and `ON SIZE ERROR` handles it) | **closed** — fixed in the interpreter at 1.91.222 (`f29f58cf`, branch `fixes-compute-size-error`; merge into `main` pending the operator) and forward-ported to `2.x.x` as 2.0.50 (`7a8e4c1f`), pinned by `cobolt-runtime/tests/test_interpreter_parity.rs::compute_division_by_zero_runs_on_size_error`. `features-2x` does not carry the interpreter half yet (nor rows 11/12's); when it is brought up to `2.x.x`, `arith_table.rs::compute_division_by_zero_is_a_size_error` must move the case into the table (its interpreter assertion turns red by design) |
| 19 | A DataGrid bound to an INDEXED file, on a web form (WASM-005 T9) | the generated backend program reads and writes through the generated file facade with COBOL verbs: a COMP/COMP-3 field shows its **value**, a signed field shows its `-`, and Save validates every change and then writes, with **no rollback** if a write fails partway | the desktop grid shows a cell from the record's bytes (`format_field_display`: COMP/COMP-3 in hex, an overpunched sign dropped) and saves all or nothing with a rollback (`grid_unit.rs`) | neither: an accepted difference | **accepted by the operator, 2026-10-23** (WASM-005 T9, option (b); spec AC7 amended). The SQL-bound grid has no difference. **Narrowed at implementation (2026-10-23):** the third difference does not arise — the generated SAVE validates every change, writes, and then uses the COBOL `COMMIT` verb, or the `ROLLBACK` verb when a write fails (`interpreter.rs` `Stmt::Rollback` undoes an open INDEXED file's changes since the last COMMIT), measured by `cobolt-server/tests/generated_backend.rs::an_indexed_grid_is_read_and_saved_through_its_generated_programs` (a taken key at the second write leaves the first insert undone). The cell differences (COMP/COMP-3 value, signed `-`) stand |
| 20 | A bound DataGrid's `Save()` of an edited row, and a refresh under concurrent writers, on a web form (WASM-005 T15) | an `UPDATE` carries **every cell as displayed** and the generated SAVE writes every non-key field with no compare against what was loaded; the rows come **window by window by offset**, so a row inserted or deleted by someone else between two windows is shown twice or skipped | the desktop overlays only the **edited** fields on the file's current record (or `SET`s only the edited columns) and fails `96` when an edited field changed since the load; it reads the whole file in one pass | the desktop: no lost update, no duplicated or skipped row | **open — concurrency, WASM-023** (plan O3 parks it there; found by the DataGrid guardrail review of T15, 2026-10-24). The fix would carry the previous value, or an "unchanged" marker, per cell in the change so the SAVE can compare or skip, and page by key rather than offset. Recorded here so it is not read as a defect of either engine |
| 21 | `RefreshBinding()` and `Save()` of a remote-bound DataGrid, in the browser (WASM-005 T16) | the **player** makes the calls (the plan: bindings are host-driven): `RefreshBinding()` answers the count the grid shows *now* and the rows arrive with the backend's answer, window by window; `Save()` answers `98` while the unit is on its way, and `CommitStatus`, `SavedRows`, `onSaved` or `onCommitError` carry the outcome | the interpreter waits for the backend inside the method and answers the count, or the save's status (T15) | neither: a module's method call is synchronous and the network is not; the events are the portable way to read a save's outcome on both | **by design, to confirm by the operator** (2026-10-24). A program that reads `Save()`'s answer as the outcome works on the desktop only; one that handles `onSaved`/`onCommitError` works on both |
| 22 | A remote-bound indexed grid's row identity, in the browser (WASM-005 T16) | the binding's key field — at most one, as the Designer records it (`key_field`) | the `.cidx` primary key, every part of it (T15, after the guardrail review) | the desktop: the generated SAVE expects the primary key's parts | **open — the Build and the description**: the Build should write the `.cidx` primary key parts into the form description's binding (WASM-016 R3), so the player sends what the SAVE expects; until then a composite key, or a key the Designer did not mark, saves wrongly on the web |
| 23 | A key cell the program changes in a remote-bound grid, in the browser (WASM-005 T16) | a `DELETE` of the loaded row and an `INSERT` of the new one: the player tells rows apart by key only | refused, `21`: the interpreter keeps the edit and knows which cell changed | the desktop | open — WASM-004 class A: the browser grid has no operator cell editing yet, so the changes a save carries are the program's own (`AddRow`, `DeleteRow`, `SetCellValue`); the edit ledger the interpreter has comes with the editing |

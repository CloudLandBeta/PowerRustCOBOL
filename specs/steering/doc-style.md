# Documentation style — PowerRustCOBOL

> *How the docs read.* Companion to `docs.md` (*what maps to what*). The hard
> constraints (English canonical only, never "cobolt", COBOL identifiers English,
> i18n) live in `tech.md` — follow those; this file is about prose and layout.
> Applies to `developers-guide-en.md`, the manuals, `README.md`, and any new doc.

## Text style

### Voice & tense
- **Second person, present tense, active voice:** "The IDE regenerates the code…",
  not "The code will be regenerated by the IDE…".
- Lead with the point; cut filler ("basically", "in order to", "simply").
- One idea per sentence; prefer short sentences over semicolon chains.

### Paragraphs (size)
- **2–4 sentences, ≤ ~5 lines.** One topic each.
- If a paragraph starts enumerating things ("first… also… and…"), convert it to a
  list. If it exceeds ~6 lines, split it.
- No wall-of-text: put a heading, list, table, or diagram between dense passages.

### Bullets & numbered lists (right usage)
- Use a list only for **genuinely parallel items** — options, features, steps.
  Keep narrative as prose, not bullets.
- **Ordered steps → numbered list**; unordered set → bullets.
- Rule of thumb: **3+ items** earn a list; for 2, a sentence usually reads better.
- **Parallel grammar:** every item starts with the same part of speech (all verbs,
  or all nouns).
- **One line per item** ideally; nest **at most one** level deep.
- **Term — definition** items: bold the lead term, e.g.
  `- **Themes.** 28 colour themes…`.
- Don't end bullets with mixed punctuation; be consistent (either all periods or
  all none) within a list.

### Titles & subtitles (hierarchy, not font size)
- Markdown has no "font size" — the **heading level encodes hierarchy**; the
  renderer/theme sets the visual size. Never fake a heading with bold text.
- **`#`** — one per document (the title). **`##`** — top-level sections
  (numbered in the guide: `## 13. The RustCOBOL language`). **`###`** —
  subsections. Avoid going past **`####`**; if you need `#####`, restructure.
- **Don't skip levels** (no `##` → `####`).
- **Sentence case** for headings ("Building a distributable binary"), keeping
  product/keyword casing (`PowerRustCOBOL`, `PROCEDURE DIVISION`).
- Keep titles short and stable — the `docs.md` registry and ToC links depend on
  their GitHub anchors; renaming a heading is a breaking change to those links.

### Colour & emphasis
- **Body text is monochrome** — convey emphasis with **bold** (key terms, first
  use) and *italics* (subtle stress, file/format names), never colour. Don't
  over-bold; if everything is bold, nothing is.
- Colour appears only in **diagrams** and the **IDE renderer's theme** — never
  hard-code colours in prose, and never rely on colour *alone* to carry meaning
  (accessibility): pair it with a label or shape.
- In Mermaid, keep the palette minimal: the default plus **one** accent for the
  element you want to highlight.

## Diagrams (when, and how)

- **Create a diagram when a relationship is clearer seen than read:** flows
  (event loop, build pipeline), architecture (the three pieces), data movement,
  or state transitions. **Don't** diagram a 2–3 step sequence a sentence handles.
- One concept per diagram; aim for **≤ ~7 nodes**; **label the edges**.
- Always pair a diagram with a sentence of lead-in context — the diagram
  supports the prose, it doesn't replace it.
- Use **Mermaid** fenced blocks (```` ```mermaid ````) so they render inline in
  the IDE's documentation viewer and on GitHub.

## Code samples
- Fenced blocks with a **language tag**: `cobol`, `sh`, `rust`, `toml`, `mermaid`.
- COBOL in **fixed format** with correct columns; comments use `*>`. Keep samples
  minimal — show the point, not a whole program.
- Verify samples against the current code before publishing (verify-first); a
  wrong example is worse than none.

## Callouts (consistent markers)
- `> ⚠️ **Caveat.** …` — limitations / gotchas.
- `> **Note.** …` — helpful asides.
- `> 📷 **Screenshot needed — \`name.png\`** …` — image placeholder for `/doc-shots`.

## Tables
- Use for **reference matrices and comparisons** (controls, themes, mappings).
  Keep cells short (a few words); push detail into prose. Don't hard-wrap inside
  cells.

## Mechanics
- Wrap prose at **~80–100 columns** for clean diffs (the guide wraps ~80); never
  wrap inside tables or code.
- One blank line between blocks; a horizontal rule (`---`) between top-level
  sections where the guide already uses them.

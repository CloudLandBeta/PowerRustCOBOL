# Plan — the identity backend (the backend half of WASM-009)

- **Spec:** [spec.md](spec.md). **Status: DESIGN AND RESEARCH ONLY - the backend half (R4, R7-R10, R12) is NOT implemented.** No module `crates/cobolt-server/src/identity/` exists in the build, no adapter is compiled, and no identity test has run. What exists is this plan (decisions, the researched provider facts) and **uncompiled, unwired, untested drafts** of the module in [drafts/](drafts/) (see section 7). The Authentication **control** (R1-R3, R5's browser half, R6's page half, AC1, AC5, AC9) is the control/player work and is not part of this plan either.
- **Written:** 2026-10-20 by the implementing agent. The capability table below was **researched on 2026-10-20 from each product's current documentation** (a research pass read the pages named in §6; every fact carries its source). Facts the documentation did not state are marked **UNVERIFIED** and the adapters treat them as configuration, never as assumptions.
- **Live tests are the operator's (and would come after the implementation).** No real Cognito pool, Entra tenant or Keycloak realm was used and none was available; the adapters are tested against a local mock identity provider that speaks each product's documented wire shapes (§5). §7 lists exactly what remains for a live run.

## 1. Decisions

| # | Decision | Why |
|---|---|---|
| **D1** | **One adapter interface** (`IdentityProvider`): `sign_in`, `respond_to_challenge`, `sign_up`, `confirm_sign_up`, `resend_code`, `forgot_password`, `confirm_forgot_password`, `refresh`, `sign_out`, plus `flow()` and `capabilities()`. Each operation returns a closed result type that already carries the **generic** failure form (R10); an adapter cannot return "no such user". | R8: a fourth provider is an adapter, not a change to the control. |
| **D2** | **The flow is chosen per provider** (R8b, operator 2026-10-19) and the default is fixed by what the documentation allows (§2): **Cognito in-app; Keycloak hosted; Entra hosted**, with Entra External ID's *native authentication* as an opt-in `in-app` mode for **external tenants only**. | Cognito documents every self-service operation as a public JSON call; Keycloak's direct-grant "MUST NOT be used" (RFC 9700) and has no registration/reset API; Entra workforce's only in-app flow is ROPC, which fails for MFA users. |
| **D3** | **The token the frontend sends is the provider's own access token** (Q2), validated by the backend (WASM-003 R10). The backend mints nothing. | No key custody; the issuer's rotation just works. |
| **D4** | **Identity programs are public programs of the backend** (R7) - `AUTH-SIGN-IN`, `AUTH-SIGN-UP`, `AUTH-CONFIRM`, `AUTH-RESEND`, `AUTH-FORGOT`, `AUTH-RESET`, `AUTH-MFA`, `AUTH-REFRESH`, `AUTH-SIGN-OUT`, `AUTH-START-HOSTED`, `AUTH-FINISH-HOSTED` - **generated as COBOL programs** that take `AUTH-REQUEST` and return `AUTH-RESULT` (groups in a generated copybook `COPYBOOKS/AUTH-GROUPS.cpy`), whose body is one inline built-in, `COBOL::"AUTH-OP" ( "<OP>" AUTH-REQUEST AUTH-RESULT )`. The built-in lands in the identity service through a runtime hook (`BackendHooks.identity`), so a provider conversation (secrets, the code exchange) never sits in COBOL, while the mapping, the validation, the limits and the log are exactly those of any program, and the frontend's Check validates a call to them like any other. *(Design decided; the built-in, the hook and the generator are drafted in `drafts/` but not built.)* |
| **D5** | **The refresh credential never reaches page script** (R5): on the web the backend sets it in an `HttpOnly; Secure; SameSite=Strict` cookie on the HTTPS surface (`/auth/refresh` and `/auth/signout`), so the sign-in programs return **only** the access token and its expiry; the refresh token is held by the HTTP response header. Mobile uses the OS store (WASM-012), so the sign-in program also returns it when the caller declares `client = "native"`. | WASM-003 Q3: the backend serves a small HTTPS surface. |
| **D6** | **Generic failures and constant-ish timing** (R10): every sign-in failure is `AUTH-FAILED` ("the user name or password is not correct"), every reset request is `AUTH-RESET-REQUESTED`, whatever the provider said. A failed sign-in is padded to the median of successful ones' time (a floor of 250 ms) so timing does not separate "unknown user" from "wrong password". | AC3. |
| **D7** | **Rate limits are the backend's own** (R10) — per source address and per account, 10 attempts a minute by default — **in addition to** the provider's lockout, which is documented in §2 and relied on, not reimplemented. | |
| **D8** | **reCAPTCHA v3 is verified server-side by `siteverify`**, with the secret only in the backend configuration; **action**, **hostname** and **score** are checked; a token is single-use (the backend remembers the tokens it accepted for two minutes). The Enterprise `CreateAssessment` path is **not** implemented: it needs a Google Cloud project and an API key the operator must provide; the adapter interface (`CaptchaVerifier`) is where it goes. See §4 for the fail-open trap. | The classic endpoint still works and is what the spec names; Google's own migration notice (§4) is recorded for the operator. |

### 2.1 AWS Cognito user pools

| Question | Finding |
|---|---|
| In-app flow | Public operations need no AWS credentials [C1]. `InitiateAuth.AuthFlow`: `USER_AUTH` (choice-based), `USER_SRP_AUTH`, `USER_PASSWORD_AUTH`, `CUSTOM_AUTH`, `REFRESH_TOKEN_AUTH`, `REFRESH_TOKEN`; the app client must allow it (`ExplicitAuthFlows` `ALLOW_*`) [C2][C24][C26]. AWS recommends SRP for a custom-built password sign-in [C21]. A client with a secret needs `SECRET_HASH` on every call (HMAC-SHA256 of `username + client_id` keyed with the client secret) [C25]. |
| MFA | `ChallengeName` + `Session` come back; the answer is `RespondToAuthChallenge` with `ChallengeResponses`: `SMS_MFA_CODE`, `SOFTWARE_TOKEN_MFA_CODE`, `EMAIL_OTP_CODE`, `NEW_PASSWORD`, `ANSWER` (for `SELECT_MFA_TYPE`), always with `USERNAME` (+`SECRET_HASH`) [C3]. TOTP enrolment: `MFA_SETUP` → `AssociateSoftwareToken` → `VerifySoftwareToken` [C2][C22]. Session lifetime 3 min default (3-15) [C19][C24]. Email MFA needs SES and the Essentials/Plus plan [C22]. *Doc inconsistency:* the lists name both `EMAIL_MFA`/`EMAIL_MFA_CODE` and `EMAIL_OTP`/`EMAIL_OTP_CODE` [C3] — the adapter accepts both names and a live test must settle it. |
| Self-service (all public JSON, `ClientId` required) | `SignUp` {Username, Password, UserAttributes[{Name,Value}]} → {UserConfirmed, UserSub, CodeDeliveryDetails}; `ConfirmSignUp` {Username, ConfirmationCode}; `ResendConfirmationCode` {Username}; `ForgotPassword` {Username} (needs self-service recovery configured, else `InvalidParameterException`); `ConfirmForgotPassword` {Username, ConfirmationCode, Password} [C4]-[C8]. |
| Refresh / sign-out | `InitiateAuth` `REFRESH_TOKEN_AUTH` {`REFRESH_TOKEN`} — **unavailable when refresh-token rotation is on**, where `GetTokensFromRefreshToken` is used [C9]. `RevokeToken` {ClientId, ClientSecret, Token}; `GlobalSignOut` takes the user's access token. A revoked JWT still passes offline signature/exp checks — check `origin_jti` revocation through Cognito if it matters [C10][C11]. |
| Token facts | `iss` = `https://cognito-idp.{region}.amazonaws.com/{poolId}` (an "updated issuer" `https://issuer-cognito-idp…` exists; read `issuer` from discovery) [C13]. JWKS `…/.well-known/jwks.json`. RS256; **access and ID tokens are signed with different keys** [C11][C12]. **Access token:** `token_use`="access", `client_id`, **no `aud`**, `scope`, `cognito:groups`, `username`, `origin_jti`. **ID token:** `token_use`="id", `aud`=client id. API sign-in tokens carry only the scope `aws.cognito.signin.user.admin` [C12]. Validate `exp`, `iss`, `token_use`, `client_id` [C11]. |
| Hosted flow | `/oauth2/authorize` (PKCE optional, S256 only, code valid 5 min), `/oauth2/token` (`client_secret_basic`/`client_secret_post`), `/logout`, `/oauth2/revoke` [C14]-[C17]. Redirect URI: absolute, pre-registered, https except `http://localhost` [C21]. Access token 1 h default (1 s-1 day), refresh 30 days default (60 min-10 y), rotation optional with ≤60 s grace [C9][C24]. Third-party IdP sign-in only through managed login [C19]. |
| Limits / enumeration | Per-Region quotas: UserAuthentication 120 RPS, UserCreation 50, UserAccountRecovery 30 (not adjustable), UserResourceRead 50 [C18]. Lockout after 5 failed password attempts, 1 s doubling to ~15 min (documented as subject to change) [C19]. `PreventUserExistenceErrors`: API default LEGACY (returns `UserNotFoundException`), console default ENABLED; `SignUp` always returns `UsernameExistsException` [C20]. |

| Question | Finding |

Default for new clients **UNVERIFIED** (an old upgrade note says disabled [K4]). No MFA challenge/response API is documented (community: an OTP is a `totp` form parameter, a missing one gives the same 401 [K7] — **UNVERIFIED** officially). |

## 4. reCAPTCHA v3 (researched 2026-10-20)

- **Classic verification** (what R4 names): `POST https://www.google.com/recaptcha/api/siteverify` (or `www.recaptcha.net`), form parameters `secret` (required), `response` (required), `remoteip` (optional) [R1]. Answer: `success`, `score` (0.0-1.0), `action`, `challenge_ts`, `hostname`, `error-codes` (`missing-input-secret`, `invalid-input-secret`, `missing-input-response`, `invalid-input-response`, `bad-request`, `timeout-or-duplicate`) [R1][R2]. A token is valid **2 minutes** and verifiable **once** [R1]. Suggested threshold 0.5 [R2].
- **Status in 2026:** the classic pages carry "This page is deprecated" and point to Google Cloud; **classic keys can no longer be created**, existing keys keep working and are being migrated into Cloud projects; Google says to use `CreateAssessment` for new integrations [R1][R3][R4][R5].
- **A fail-open trap** [R1]: without billing, over the free quota (10,000 assessments a month [R5]) `siteverify` answers **HTTP 200, `success: true`, score 0.9 and the message "Over free quota."** The adapter therefore treats any answer carrying that message as a **failure** (`recaptcha-quota`), never as a pass.
- **Decision:** `siteverify` is implemented (the spec's R4, and the endpoint a migrated key still honours with its "legacy secret"); `CreateAssessment` (`POST https://recaptchaenterprise.googleapis.com/v1/projects/{project}/assessments?key=…`, body `event{token, siteKey, expectedAction, userIpAddress}`, answer `tokenProperties{valid, invalidReason, hostname, action}` and `riskAnalysis{score}` [R6][R7]) is **not** implemented here because it needs a Cloud project and an API key the operator must create; `CaptchaVerifier` is the seam.

- **Drafts.** [drafts/](drafts/) holds about 2,300 lines of first-pass Rust for the module (`mod.rs`, `cognito.rs`, `keycloak.rs`, `entra.rs`, `oidc.rs`, `recaptcha.rs`, `ops.rs`, `session.rs`, `http.rs`, `generate.rs`, `idp_mock.rs`), saved with the extension `.rs.draft` so the build ignores them.

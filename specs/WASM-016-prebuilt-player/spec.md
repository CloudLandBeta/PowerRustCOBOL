# Spec — The player: a prebuilt Leptos form engine for the browser

- **Status:** draft (needs `/clarify`)
- **Folder:** specs/WASM-016-prebuilt-player/
- **Author:** Anthropic Claude Codex Agent   **Date:** 2026-10-19
- **Branch:** `features-2x` (version line 2.x.x). Part of the WASM series, see `specs/WASM-INDEX.md`.
- **Origin:** the operator's decision of 2026-10-19 on the question WASM-002 Q7 / WASM-010 Q10 left open: ***two `.wasm` files — a prebuilt Leptos player that draws any form, plus the generated COBOL module. A Web build becomes "emit the
  module and copy the player", with no Rust toolchain.*** The player had no spec of its own; this is it.
- **Depends on:** WASM-002 (the bundle and host page), WASM-010 (the module and the host API). **Carries:** the implementation side of WASM-004 (the controls), WASM-007 (properties to CSS), WASM-009 (the Authentication control),
  WASM-005 (the connection to the backend), WASM-011 (routing), WASM-013 (the policies it must obey).

## 1. Overview

A Web or Mobile application is **two WebAssembly files**. The **program module** is the COBOL, generated by the compiler (WASM-010). The **player** is everything else the application needs in a browser: it reads a **form description**,
builds the DOM for any form, applies the CSS, routes the user's events to the program, performs what the program asks (set a property, call a method, make a remote call), and owns the connection to the backend. The player is written
once, in Rust with **Leptos**, **built when the product is built**, shipped with the IDE and **copied** into each bundle. It is the browser's counterpart of the desktop **form host** (`cobolt-form-host`).

Because the player is prebuilt and generic, a Web build needs no Rust toolchain: the compiler emits the module, writes the form descriptions and the stylesheet, copies the player, writes the host page. A Mobile build still compiles a Tauri
shell per application (WASM-012), but the frontend inside it is the same two files.

### What exists today (checked 2026-10-19, `main` at 1.91.217)

- **The desktop form host** is `crates/cobolt-form-host`: `host.rs` alone is 13,390 lines, `seeding.rs` 1,277 (`seeding.rs:399-500` seeds the data bindings into the controls). It implements a designed form window **once** — control state,
  backdrop, window properties, entrance and exit effects (spec 038), the window lifecycle (spec 037), event dispatch and pacing — and is shared by `rcrun run-form` and the compiled applications (spec 042). It is native (`rfd`, `pollster`, eframe)
  and is not reusable in a browser.
- **A lesson already learned here.** Spec 042 records that *three hand-maintained form hosts had drifted*, and that the one every end user received — the built application — was the poorest. A browser player is a **fourth** implementation of
  the same behaviour; unless it is measured against the others it will drift too (R14).
- **The forms' data is serialisable already:** `.cfrm` is XML with a model in `cobolt-forms` (`Form`, `Control`, `PropValue`, `EventBinding`, data bindings, breakpoints, `layout`); the model part builds without egui
  (`cobolt-runtime/Cargo.toml:149`) but carries ungated native dependencies (WASM-002).
- **A precedent for a committed prebuilt asset with a freshness test:** `assets/knowledge/chunked.data` (12.4 MB) is built by an example, committed, and guarded by `prebuilt_chunked_kb_matches_the_published_documentation`
  (`cobolt-ide/src/grace_host.rs:4780`) — the same shape the player can take (R12).
- **Nothing exists in the browser:** no Leptos, `wasm-bindgen`, `web-sys` or `trunk` in the workspace's own dependencies (WASM-002).

## 2. Goals / Non-goals

- **Goals:**
  - One **prebuilt player** that draws any form from a description, with no per-project Rust.
  - The player is the **single implementation of every web control** and of the form-host behaviours (window properties, lifecycle, effects, event dispatch, pacing).
  - A defined **form-description format**, a **host API** the player implements for the program module, and a **version triple** that makes a bundle consistent by construction.
  - The player owns the **connection to the backend** (WebSocket, token, framing, reconnection), so the program module has no network at all.
  - Ships with the IDE; **no Rust toolchain on the developer's machine** for a Web build.
- **Non-goals:**
  - Per-project Leptos code, developer-written components, and `Custom { plugin_id }` controls on the web in v1.
  - Server-side rendering.
  - Replacing the Form Designer's egui canvas.
  - A public component library for third parties.

## 3. User stories

- As a developer, I want to build a web application without installing Rust, so that a COBOL developer can ship to the web.
- As a developer, I want the form I designed to appear in the browser as the Preview showed it, because both are the same player.
- As a maintainer, I want each control implemented once for the web, so that a fix reaches every application at its next build.
- As a security reviewer, I want one small, audited piece of browser code that touches the DOM and the network, so that I review it once.

## 4. Requirements (EARS)

**The artefact**
- **R1 (ubiquitous):** The player shall be **one prebuilt WebAssembly module** (with its loader) built from Rust and Leptos when the product is built, shipped with the IDE, and **copied, never compiled**, into every Web and Mobile bundle. A Web build shall need no Rust
  toolchain, `wasm32` target or bundler on the developer's machine.
- **R2 (ubiquitous):** The bundle shall be exactly the **player** (in a plain and a threaded variant, R13c) and the **generated program module** — one for the whole project, in a multi-memory and a single-memory variant (WASM-010, WASM-017 R1, R9) — plus the host page, the form descriptions, the stylesheet and the assets; nothing else executes.

**The form description**
- **R3 (event):** When the developer builds, the Build shall write, for each form, a **form description**: a versioned, serialised form (its controls, their properties, layout and breakpoints, the events bound to handlers, the data bindings, the stylesheet reference) derived from the form file (`.wcfrm` or `.mcfrm`), and
  the player shall draw any form from it. The same description shall feed the **Preview** (WASM-008) and the Build.
- **R4 (ubiquitous):** The description shall contain **no secret** and no program code; the handler code is in the program module, referred to by id.

**What the player does**
- **R5 (ubiquitous):** The player shall implement each control of classes A and B (WASM-004) **once**, with the properties, events and methods of the model, the property-to-CSS table of WASM-007 R1, `CssClass`, `Style` and the form stylesheet, and the accessibility
  behaviour of WASM-004 R10; and it shall implement the Authentication (WASM-009) and WebLink (WASM-006) controls.
- **R6 (ubiquitous):** The player shall provide, in the browser, what the desktop form host provides for a designed form: the form's window properties and backdrop, the entrance and exit effects, the window lifecycle events, event dispatch to the bound handlers, and the pacing of
  timers and animations — each as the existing specs (037, 038, 042) define them, or with the difference documented.
- **R7 (event):** When the user acts on a control, the player shall deliver the event (an id, the control, the parameters) to the program module (WASM-010 R10) and, while the module runs, carry out what it asks through the **host API** (WASM-010 R12): read and write a control's
  property, call a control's method, write `DISPLAY` output to the console, give the time and a random number, and make a remote call.
- **R8 (event):** When the module stops at a call that waits (WASM-010 R9), the player shall perform the wait — a remote call, a dialog, a timer — and resume the module with the answer; events raised meanwhile shall be queued in order (WASM-005 R9).
- **R9 (ubiquitous):** The player shall own the **connection to the backend**: it opens the WebSocket, adds the bearer token (WASM-009 R5), frames and correlates calls (WASM-003 R6, WASM-014), reconnects with back-off, refreshes the token, and enforces the timeouts; the program
  module sees only "send this JSON, give me the answer" (WASM-005 R8). The player shall connect only to the configured backend addresses.
- **R10 (ubiquitous):** The player shall implement routing and the two application styles (WASM-011): the SPA's shell, routes and history, and the standalone forms' pages, windows and `super` messaging.

**Consistency and versions**
- **R11 (ubiquitous):** The player, the form-description format and the host API shall each have a **version**; the Build shall copy the player that matches the compiler that emitted the module, and the module shall refuse to start against a player that lacks a host-API entry it
  needs (WASM-010 R12). A bundle is therefore consistent by construction; a player and module that disagree are a build error, never a run-time surprise.

**Building and shipping it**
- **R12 (ubiquitous):** The player shall be built by a step of the product's build (a workspace example, as `build_chunked_kb` is) from its source, its output shall be committed or produced at release (Q2), and a **freshness test** shall fail when the shipped player is not the one its source produces. The IDE shall find
  the player the way it finds its other bundled assets. The build profile (size-first, `panic = "abort"`, `wasm-opt`), the pinned tools and the rule against `wasm-pack` are WASM-017 R16–R17.
- **R13 (ubiquitous):** The Build shall report the player's size and the sizes of any parts loaded on demand (Q3), and the player shall load heavy controls (charts, maps, the Viewer) **on first use** where that is possible, so that a form without them does not pay for them. Those parts follow the same loading and disposal rules (WASM-017 R3, R5); the Canvas 2D and Canvas 3D controls and the graphics objects (WASM-018) are such parts.
- **R13c (ubiquitous):** The player shall be built in **two variants** from one source: **plain** (stable Rust, no shared memory) and **threaded** (a pinned nightly toolchain, a rebuilt standard library, atomics and shared memory, `wasm-bindgen-rayon`; WASM-017 R16). It shall use **Rayon** for its parallel work — image and chart work, DataGrid sorting and filtering, physics, canvas rasterisation — on a worker pool, with the
  same results on the plain variant, which runs the same code sequentially (WASM-017 R19, WASM-018 R20); the host page chooses the variant by `crossOriginIsolated`.
- **R13b (ubiquitous):** Every Rust object the player exposes to JavaScript through `wasm-bindgen` shall have an explicit disposal called by `unmount()` and on teardown, the objects exposed shall be few and listed, a panic shall end the instance cleanly with a readable error and a reload action, and the player shall never hand JavaScript a view over its own memory
  that outlives a call into it (WASM-017 R10, R14, R15).

**Assurance**
- **R14 (ubiquitous):** The player shall be held equal to the desktop form host by measurement: the reference form of WASM-004 R11 and the lifecycle, effects and event-order checks of specs 037/038/042 run against both, and a difference is documented or fixed (the drift of spec 042 is the failure this prevents).
- **R15 (ubiquitous):** The player shall obey the policies of WASM-013: no API that inserts an HTML string — the Viewer builds DOM nodes from an allow-listed, parsed tree instead (WASM-013 R5) — which a source search proves, no `eval`, a strict CSP, no network except the backend and the bundle's own files, and no secret in the player, the descriptions or the stylesheet.
- **R16 (state):** While the Preview (WASM-008) is open, the player shall accept a **new module, form description or stylesheet without reloading itself**, so that the Preview updates in place.
- **R17 (constraint):** A Desktop project is unchanged; the desktop form host remains the host of desktop applications.

**Form layers (spec 091, adapted to HTML)**
- **R18 (ubiquitous):** The form description shall carry the layers in stack order, each with its name and its backdrop properties other than `Visible` (spec 091 R39), and each control with its `Layer` (default `Form`). A form with no layers shall carry none of this (WASM-004 R24).
- **R19 (state):** The player shall hold each layer's `Visible` state for each form instance, start every layer hidden when the instance is created, apply the program's changes on the next frame, and release the state with the instance (WASM-017 R5), so that a form opened again starts hidden as its description says (spec 091 R35; WASM-004 R15).

## 5. Acceptance criteria

- [ ] **AC1** — On a machine with no Rust toolchain, a Web project builds to a bundle that contains exactly the player (plain and threaded) and the program module (multi-memory and single-memory variants), the host page, form descriptions, stylesheet and assets, and runs in a headless browser.
- [ ] **AC2** — A form with one control of every class A and B type is drawn by the player from its description, with the properties set; the DOM shows each, and the property round-trip of WASM-004 R11 passes.
- [ ] **AC3** — A click on a bound button reaches the program module's handler; a property written by the handler appears in the DOM; a method call reaches the control; `DISPLAY` reaches the console.
- [ ] **AC4** — A handler that makes a remote call stops, the player performs it against a test backend with the token attached, and the handler resumes with the answer; two events raised meanwhile are handled afterwards in order.
- [ ] **AC5** — With the backend stopped the player reconnects with back-off; the program sees `ON EXCEPTION` for the call in flight and not for later ones after reconnection.
- [ ] **AC6** — A bundle whose player lacks a host-API entry the module needs fails the Build; a module started against such a player refuses to start with a message.
- [ ] **AC7** — The freshness test fails when the player's source changes without the shipped player being rebuilt, and passes when it is rebuilt.
- [ ] **AC8** — The Build reports the player's size; a form with no chart, map or Viewer does not load their parts (a test inspects what was fetched).
- [ ] **AC9** — The reference form and the lifecycle, effect and event-order checks give the same results on the player and on the desktop form host, except for the documented differences.
- [ ] **AC10** — A source search finds no HTML-string-inserting API in the player, the Viewer included; the player runs under the generated CSP; a connection to an address outside the configured backend is refused.
- [ ] **AC11** — In an open Preview, replacing the module, a form description and the stylesheet each updates the page without a reload of the player.
- [ ] **AC12** — A form with layers opened twice in a row starts both times with every layer hidden, and no layer state survives the release of the instance (R19).

## 6. Constraints & steering check

- **i18n:** the player's own fixed texts (loading, error, retry) are the host page's (WASM-002 R15) and are translatable by the developer; IDE strings (the Build report) are six languages.
- **Generated-code contract:** form descriptions, the host page and the stylesheet are generated artefacts, never hand-edited; the player is a built artefact with a freshness test, like `chunked.data`.
- **Tech steering:** the player is the one place where Leptos, `wasm-bindgen` and `web-sys` enter the workspace; they go through the dependency guards, the licence check and MSRV 1.92 at `/plan`. The toolchain they need (the `wasm32` target, the bundler) is needed **by the product's build**, not by the developer's.
- **Size:** the committed player enlarges the repository (a precedent: the 12.4 MB `chunked.data`); the plan states the cost and how it is kept down (R13).
- **Docs:** `docs/` untouched on 2.x.x.
- **Fix vs feature:** **feature** (`features-2x`).

## 7. Open questions

- **Q1 — The form-description format:** JSON (easy to inspect and diff), a compact binary, or the `.cfrm` XML itself? Recommended: JSON, versioned, with a binary option later if the size matters.
- **Q2 — Committed or built at release.** Commit the built player (as `chunked.data` is: the IDE works from a clone with no extra step) or build it in the release pipeline and have a developer's checkout build it once? Recommended: committed, with the freshness test.
- **Q3 — One file or on-demand parts.** A single player file is simplest; heavy controls loaded on first use (R13) mean several files and a loader. Recommended: split from the start along the class B controls.
- **Q4 — How much of the form host's behaviour reaches the browser in v1.** Entrance and exit effects, window states and positions (R6) have no obvious browser meaning for an SPA; which are kept, mapped or dropped? Decide per behaviour at `/plan` and list the differences (R14).
- **Q5 — Extensibility.** The developer cannot add Leptos code in v1 (non-goal). When `Custom` controls and external crates reach the web (WASM-INDEX, plugins on `wasm32`), is the answer a second prebuilt "player with plug-ins", or loading plug-in modules? Out of scope here; note that the two-module design does not forbid either.
- **Q6 — The player in two builds of the IDE.** Because the player is shipped with the IDE, an IDE upgrade changes the player a project builds with; confirm that a rebuild always uses the current one, and whether an old project can pin an older player (the contract of R11 makes a mix a build error).

# Plan — The Backend project and the secure frontend–backend channel

- **Spec:** [spec.md](spec.md). **Status:** the backend crate, the headless build path, the channel and the token checks are implemented and tested over a real TLS loopback (M3); the contract half (WASM-014) is M4 and the identity half (WASM-009 backend) is M5 — see their plans. The IDE panels, the scaffold of R22 and the frontend half of R23/AC10 are **not** part of this work and are listed under *Not done*.
- **Written:** 2026-10-20, by the implementing agent while the operator was away. Every decision below was taken without asking; each states what it chose, why, and what the alternative cost — for the operator to overturn.
- **Evidence** is in the last section; nothing is claimed there that was not run.

## 1. Decisions (answering the spec's open questions)

| Q | Decision | Why | Alternative |
|---|---|---|---|
| **Q2** statefulness | **Fresh `WORKING-STORAGE` per call**: every call builds its own interpreter from the exported program's AST; nothing survives it. State lives in files or a database. | It is the model that scales, and it cannot leak between users (R18). A test (`concurrent_callers_get_their_own_results_and_no_state_survives_a_call`) runs 8 concurrent users, 25 rounds each, calling a customer program and a counter program: every answer carries its own caller's subject and every counter answers `1`. | A per-connection instance would need a session lifecycle, eviction and a story for reconnection. |
| **Q3** HTTP endpoints | **One**: `GET /health` on the TLS port (and, optionally, on a separate plain loopback `health_listen`). The WebSocket is the contract; the refresh cookie and the identity redirect of WASM-009 arrive with the identity module (M5) on the same listener. | A probe needs no WebSocket; everything else is the WebSocket. | A general HTTP router now would be speculative. |
| **Q4** idempotency | **None by default**; declared per export (`idempotent = true`). The semantics belong to WASM-014 (M4). | Safe by default. | — |
| **Q5** development token | **Allowed in a development run only**, as an HS256 token signed with a secret **made fresh at every start** and printed once (`rcrun backend run`). The setting that enables it is named `unsafe_dev_token_secret`, and **a release start refuses every `unsafe_*` setting** (WASM-013 R11). The built binary is always a release start. | It is the easiest way to ship an unauthenticated backend by mistake, so there is no way to turn it on in a binary: `config.rs` has the rule and `a_release_start_refuses_every_unsafe_setting_and_a_development_start_only_warns` the test; the built-binary test runs the binary with `unsafe_allow_any_origin` and sees exit 2. The `HS256` algorithm is also refused in `auth.algorithms` — an identity provider signs with a key pair. | A fixed development secret in the project would leak with the repository. |
| **Q6** packaging | **Host only.** `rcrun backend build` produces `bin/<project>-backend` for the machine it runs on. | Spec 041. | Cross builds need toolchains this product does not own. |
| **Q7** TLS | **Both.** The binary terminates TLS with the operating system's stack (certificate files or a PKCS#12 identity); behind a reverse proxy it listens on loopback with plain `ws` and refuses a non-loopback `ws` either way (`server.listen` rule). | R5. | — |

Further decisions the spec did not ask:

1. **TLS is `native-tls`, not rustls.** `ring` and `aws-lc-rs` compile C and are barred by `dependency_guards_063` (spec 063 AC8 as amended by 103), and rustls without them has no ready provider. `native-tls` is already the project's TLS (the agents transport, `ureq` for the SDK, the HTTP bridge). The server wraps it with `tokio-native-tls`; the WebSocket framing is `tokio-tungstenite` with `default-features = false, features = ["handshake"]`, so neither pulls a TLS stack of its own. The guard `crates/cobolt-server/tests/dependency_guards.rs` reads the closure Cargo really resolves and fails on `ring`, `aws-lc-*`, `rustls*`, `openssl*`, `boring*`.
2. **JWT is `jsonwebtoken` 11 with the `rust_crypto` backend** (RustCrypto's `rsa`, `p256`, `p384`, `ed25519-dalek`, `hmac`, `sha2`): pure Rust, no C. We use it only to verify a signature and decode claims; **every policy decision is ours** (§2.3): the algorithm allow-list, the key lookup by `kid`, issuer/audience/expiry/not-before, the profile rules.
3. **A macOS fact that shaped the tests, recorded for whoever configures a certificate there:** `native-tls` on macOS imports a PEM + PKCS#8 identity only when the private key is **RSA** (`Identity::from_pkcs8` answers "Unknown format" for an EC key), and Security.framework refuses to trust a certificate whose RSA key is under 2048 bits. A deployment with an EC certificate on macOS must give the identity as PKCS#12 (`tls.pkcs12`). Linux (OpenSSL) and Windows (Schannel) accept both. The loopback tests therefore use a 2048-bit RSA certificate.
4. **A closed set of failure classes with stable numeric codes** (WASM-005 R10): `transport` 1000-1003, `authentication` 2000-2002, `authorisation` 3000, `validation` 4000-4001, `not-found` 5000, `version` 6000-6002, `limit` 7000-7004, `application` (the program's own code), `server` 9000-9002. The codes are in `cobolt-wire/src/error.rs`; the English text is for logs and developers.
5. **An unknown program name is answered as "no token" to an unauthenticated caller** (the token check runs before the program lookup, unless the program is public), so the set of exported names cannot be enumerated; an authenticated caller learns `not-found 5000`.
6. **Configuration is strict.** `deny_unknown_fields` everywhere: a misspelt security setting stops the start. Every fault is reported together, so one start shows them all.
7. **Secrets print as nothing.** A `Secret` type has a `Debug` that says `Secret(***)`; `TlsSource` prints sizes; the identity section prints the names of its settings, not their values. The dump of a resolved configuration cannot leak (test `the_tls_identity_and_the_provider_settings_print_without_their_secrets`).

## 2. Design

### 2.1 The project and the build (R1-R4, R20)
- **Project shape** (`crates/cobolt-server/src/backend.rs`): `backend/exports.toml`, `backend/src/*.cbl`, `backend/COPYBOOKS/`, `backend/backend.toml` (the deployment), `backend/contract/interface.json` (written by Build) and `backend/contract/released/<version>.json` (the interface of each released contract).
- **Exports.** `exports.toml` is the whole of what the channel can run: `program`, `roles`, `public`, `idempotent`, `independent`, `long_running`, `stream`, `directions`, `deprecated`. A program not in it is unreachable by any spelling (test: nine spellings including `../` and a NUL).
- **Loading** parses and analyses every program (all diagnostics reported together), checks that each export names a program, turns each exported program's `USING` groups and `RETURNING` group into wire layouts (`cobolt_wire::layout::from_decl`) and builds the interface description. **The exported program becomes the top-level program with every other backend program nested in it**, so an exported program `CALL`s a helper by name with the ordinary local dispatch.
- **Build** (`cobolt-compiler/src/backend_build.rs`): reads and checks the backend, writes `interface.json`, compares it with the last released contract (WASM-014 R5; a release build fails on a break, a debug build does not), generates a Cargo project and builds it. The generated project depends on `cobolt-server[server]` and `cobolt-runtime` with **only the runtime features the programs reach** (the same scan the application build uses), embeds the programs with `include_bytes!` (bincode + deflate), and its `main` is `cobolt_server::standalone::main`. **No `eframe`, no `egui`, no form host**; `crates/cobolt-server/tests/dependency_guards.rs` proves the closure. The build starts from the SDK's `Cargo.lock` (spec 101 R4) and falls back to a fresh resolution when this machine cannot supply a pinned version.
- **The compiler links only the loader.** `cobolt-server` has features `loader` (read and pack), `server`, `client` and `net`; `cobolt-compiler` takes `loader` alone, so building an application links no socket, no TLS and no token code (the guard checks that too).
- **CLI** (`rcrun backend run|describe|check|release|build [dir]`): `run` serves the backend on a loopback address with a fresh development token (the same binary logic as the built one, with the development relaxations and nothing else); `check` compares the contract with the released ones; `release` records it; `build` is the above. The IDE's Start/Stop button and Output panel are the IDE agent's; they call these.

### 2.2 The channel (R5-R8, R14, R16)
Order of everything a connection and a call go through (the security model, written once in `serve.rs`):
**Connection:** accept → connection limit → TLS → read the HTTP head within the handshake timeout → route (`/health`, or the upgrade) → **Origin check** → upgrade with the frame and message size capped → `hello` within the handshake timeout, versions negotiated.
**Call:** connection rate bucket → (non-public program) valid token → program lookup → user rate bucket → role → concurrency permits (per connection and total) → ordering ticket (unless `independent`) → the program runs on a `spawn_blocking` thread, isolated, under a deadline → the answer is projected to the contract the caller was built against.
- **Wire:** JSON **text frames** with a `t` field (`hello`, `auth`, `call`, `reply`, `error`, `ping`/`pong`, …; `cobolt-wire/src/proto.rs`). Requests carry an id, the program and one `{mode, json}` per argument; answers carry the same id; any number of calls may be in flight and answers arrive in any order. Binary frames are refused.
- **Keep-alive:** the server pings every `ping_interval_seconds` (20) and drops a connection that says nothing for `idle_timeout_seconds` (60). The client's reconnection with back-off is the client's (M4).
- **Origin:** an exact match against `server.allowed_origins` (a `*` is refused at configuration time); no `Origin` is accepted only with `allow_missing_origin` (non-browser clients).
- **Limits** (R16, all configurable, all with safe defaults): frame size 1 MiB, call timeout 30 s, per-connection 20/s burst 40, per-user 50/s burst 100, 8 concurrent calls per connection, 64 total, 1000 connections. Each is refused with its own error code (7000-7004); the test that exercises them checks the codes are distinct.

### 2.3 Tokens (R9-R13)
`jwt.rs`, in the order the checks run: shaped like a JWT and not over 16 KiB → an **allowed algorithm** (`RS256`/`ES256` by default; never `none`, never an HMAC) → the key is found by `kid` in the issuer's JWKS and, when the key names its own `alg`, it must equal the token's (the algorithm-confusion attack has nothing to bite on) → issuer in the configured list, `exp` required, `nbf` honoured, clock skew `leeway_seconds` (60, **at most 300**) → audience or app client → **access token, not identity token** by the provider's own marker, and never one carrying `at_hash` or `nonce`.
- **Profiles** (`auth.profile`, WASM-009 R8): `generic`, `cognito` (`token_use = access`, the app client in `client_id`, no `aud`, groups in `cognito:groups`), `keycloak` (`typ = Bearer`, roles in `realm_access.roles`), `entra` (`aud` the API's application id, `scp` or `roles` present). Roles can be read from any dotted claim path (`auth.roles_claims`).
- **Where the token travels (R11):** a first WebSocket message `{"t":"auth","token":…}` after the `hello` — never the URL, a query string or a sub-protocol (those end up in access logs and browser history). Calls of a connection use that token; a call may carry a fresher `token` of its own, which is how the frontend refreshes without reconnecting (R13): an expired token answers `authentication 2002`, the frontend refreshes and repeats.
- **Expiry is re-checked at every call**, not only when the token was first verified: a verified token is cached by its SHA-256 and `exp`/`nbf` are judged again each time it is used.
- **JWKS** (`jwks.rs`): fetched over HTTPS with the operating system's TLS, trusted for `jwks_ttl_seconds` (3600); an unknown `kid` may mean rotation, so one refresh is allowed, **never more often than `jwks_min_refresh_seconds` (30) whatever the cause** — a flood of tokens naming random key ids cannot turn the backend into a request amplifier against the issuer (the test sends 200 and sees one fetch). While the issuer is down the last keys keep serving, up to a day, and the log says so.
- **Claims** are available to the program through `COBOL::"WS-CLAIM" ( name value )` (read-only; any scalar claim, nested ones with dotted names, arrays comma-joined, 1024 characters at most). The token itself is never reachable by a program.
- **The development token** is HS256 with the per-start secret; it is the only HMAC the validator ever accepts and only where `dev_secret` is set, which only a development start does.

### 2.4 Hardening (R15, R17, R18, R21)
- **Payload validation (R15)** is the mapping's strict reader (WASM-005): the arguments are read into the program's LINKAGE items before it starts; an unknown key, a wrong type, an over-long string or an over-long table is refused naming the item, and the program never runs.
- **Isolation (R18):** a fresh interpreter per call, no shared mutable state but files. A panic in a program is caught and answered as `server 9001`; a run-time error is logged and answered as `server 9001` *without its detail* (the caller learns only that it failed).
- **Logs (R21):** `LogRecord` has no field that could hold a token, a password, a payload or a claim — sizes are logged, contents are not. That is stronger than a filter. One JSON line per call and per connection event; a sink trait (`StdoutSink` for the binary, `MemorySink` for tests and `rcrun backend run`). The test plants a token and a password-named field and greps the whole log.
- **Secrets (R17)** are read from `env:NAME` / `file:PATH` or written in `backend.toml` (never in a form); nothing in `cobolt-server` reads a `.cfrm`.
- **Health (R21):** `GET /health` answers `{"status":"ok","contract":…,"protocol":…,"connections":…,"calls_ok":…,"calls_failed":…}` and carries the security headers; unknown paths are 404.

### 2.5 Concurrency across connections (R19)
The PRCIDXD1 container has **no concurrency control of its own**: two openers read and write the same file. A backend serving several callers therefore needs locks the engine does not provide. `Interpreter::set_file_lock_wait(Some(d))` turns on a **server policy**: every `OPEN` of an indexed (or any non-sequential-input) file takes an advisory lock on a `<path>.lck` sidecar — **exclusive** for any mode but `INPUT`, **shared** for `INPUT` — and **waits up to `d`** (polling, 1-8 ms) for a conflicting lock to go away instead of refusing at once; after that the `OPEN` answers file status **93**. The lock is held until the file's `CLOSE` has finished flushing the engine. Programs that close promptly therefore take turns; a program that holds a file open for a long time makes everyone else wait or fail with 93, which is the correct, visible behaviour.
- **A real bug found by the test and fixed in the runtime:** `exec_close` released the advisory lock *before* the engine's `close()` had finished writing the container, so a second caller admitted by the lock read a half-written file (file status 90). With 24 concurrent writers 3 failed. The lock handle is now held to the end of the `CLOSE`. This also affects two OS processes opening a file with `SHARING`/`WITH LOCK` (the cross-process fix of 2026-09-14) and is a fix in its own right.
- SQL data needs nothing here: the database's own isolation applies per connection.

## 3. Hosts (interpreter / binary parity)
The remote-call statement and the lock policy are in the shared interpreter. The backend is a **fourth** host of the interpreter and the only one that installs the lock policy and the claims. The three form hosts do not serve calls; they *make* them, which is the client (M4).

## 4. System KB
`COBOL::"WS-CLAIM"` is in `BUILTINS`, in the compiler's built-in table, and the section *Calling the backend* documents `exports.toml`, the shared-file behaviour, the contract rules and `rcrun backend`. `assets/knowledge/chunked.data` is regenerated.

## 5. Not done in this work (stated plainly)
- **AC9, the IDE half:** starting and stopping the backend from the IDE and showing its log in the Output panel — the IDE agent's panels. The pieces they need exist: `rcrun backend run` and `cobolt_server::dev::DevServer` (start, URL, token, log lines, stop).
- **R22**, the scaffold with the authentication programs when a Web or Mobile project is created: the IDE's project creation (WASM-001); the programs themselves are M5 (WASM-009).
- **R23 and AC10**, the frontend's `connect-src` and the build-time secret scan of a frontend: the web build (WASM-002/010).
- **Windows and Linux were not run.** The code uses only `std`, `tokio` and `native-tls`; everything here ran on macOS (Darwin 24.5, aarch64). See *Evidence*.
- **A real identity provider** was never contacted: the issuer in every test is a local key pair that publishes a JWKS through a test fetcher.

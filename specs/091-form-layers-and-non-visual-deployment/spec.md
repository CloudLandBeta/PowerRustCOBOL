## 1. Overview

A form is one flat plane: every control sits on the same canvas. When a program shows and hides controls according to its own logic — an error banner, a busy overlay, the steps of a wizard — the designer still shows all of them at once, stacked on top of each other, so the form cannot be read or edited.

This feature adds **layers**. The form as it exists today becomes the **base**. Above it the developer may add layers: transparent planes, stacked in an order the developer controls, each holding its own controls. Every layer can be shown or hidden in the designer and from COBOL, so the controls that belong together appear and disappear together. A form with no layers is exactly the form it is today.

The same feature gives the **non-visual controls** — a `Timer`, an `AgentObject`, a `SqlDatabase` and the rest of the controls that paint nothing at run time — a home of their own. Today each one sits on the canvas as a card at whatever position it was dropped, among the controls that do paint. A fixed **`Non-Visuals` tab**, to the left of `Form`, holds all of them in a grid of five columns, same types together and in A–Z order. A non-visual control dropped on the form lands there by itself; one already in a form is placed there when the form opens; and selecting one and pressing Delete removes it, with its own event code.

## 2. Goals / Non-goals

- **Goals:**
  - G1 — Let the developer author overlapping, program-controlled controls on separate planes and show or hide each plane while designing.
  - G2 — Let COBOL show, hide and restyle a layer at run time by name.
  - G3 — Change nothing for a form that does not use layers: same file, same behaviour at run time. At design time the one visible change is G4: its non-visual controls move into the `Non-Visuals` tab.
  - G4 — Give the non-visual controls one organised place: a fixed tab, a grid of five columns, each control in a cell, same types together in A–Z order, arranged automatically (R46–R58).
- **Non-goals:**
  - Nested layers. Layers form one flat stack above the base.
  - Free positioning of the non-visual controls: the grid decides each cell (R49–R52).
  - Non-visual controls on a layer, or on the `Form` tab (R47).
  - A layer is not a window, a form or a program: no WORKING-STORAGE of its own, no window properties, no corner radius.
  - Layer events (`onShow` and the like), and re-stacking a layer from COBOL (Q9).
  - Replacing `Panel`, `GroupBox`, `TabControl` pages or embedded forms. They keep working inside a layer.
  - Layout inside a layer: no Dock, Anchor, flex, grid or flow (R21).

## 3. User stories

- As a developer, I want the controls of a busy overlay on their own layer, so that I can hide the overlay while I design the screen underneath.
- As a developer, I want to hide a layer in the designer and see only the layers I am working on.
- As a developer, I want a mouse click on the empty part of an overlay to reach the button underneath it, so that an overlay with a label and a close button does not block the whole form.
- As a developer, I want `SET LAY-ERROR::Visible TO TRUE` to show a layer, so that the program decides when it appears.
- As a developer with an existing application, I want my forms to load, run and save as before.
- As a developer, I want every non-visual control of a form in one tidy place, so that I find a `Timer` or a database connection without hunting for it among the controls that paint.
- As a developer, I want a non-visual control I drag onto the form to land in that place by itself, so that I never have to choose where it goes.
- As a developer, I want to select a non-visual control and press Delete, so that it goes with its own event code and nothing else is needed.
- As a developer, I want the tab I need to be in front as soon as I pick a control from the toolbox, so that I never place a `Timer` among the visual controls or a `Button` in the grid.
- As a developer, I want to click a layer and see the form with just that layer on top of it, so that I edit one layer at a time without hiding the others by hand.
- As a developer, I want to tick a layer's box without being thrown to that layer, so that I can compare two layers while I keep working on a third.
- As a developer, I want deleting a layer to ask me first and to be undoable, so that I never lose a layer's controls and code by a slip of the mouse.

## 4. Requirements (EARS)

### 4.1 Model and compatibility

- **R1 (ubiquitous):** The system shall give every form one **base** — the form as it exists today — and zero or more **layers** stacked above it.
- **R2 (ubiquitous):** A form with no layers shall load, render, run, generate COBOL and save exactly as before this feature. Saving it shall write no layer information, and a `.cfrm` that never had layers shall come back byte-identical.
- **R3 (ubiquitous):** The system shall give every control, except a non-visual one (R47), a **`Layer`** property naming the layer it belongs to. Its default is `Form`, the name of the base (the operator, 2026-10-08: the base is called `Form`; `base` was only a working name).
- **R4 (ubiquitous):** A control name shall be unique across the **whole form** — base and every layer — compared without regard to case.
- **R5 (event):** When a name would collide — a rename, a paste, a duplicate, a move between layers, or a load — the system shall refuse the rename and shall give a pasted or duplicated control the next free name. A `.cfrm` that already holds a collision shall be reported in the Output panel and shall not be repaired by deleting anything.
- **R6 (ubiquitous):** A layer shall have a name, with the same character rules as a control name and drawn from the **same namespace** as control names. `Form` and `Non-Visuals` are reserved, in any letter case, and no layer may carry either. A new layer shall be named `Layer-1`, `Layer-2`… the first free one.
- **R7 (constraint):** A form shall hold at most **64 layers** above the base (Q5). Adding another shall be refused with a message.
- **R8 (ubiquitous):** A control inside a container (`Panel`, `GroupBox`, a `TabControl` page…) shall belong to its container's layer. Moving a container to another layer shall move everything inside it.

### 4.2 Stacking and painting

- **R9 (ubiquitous):** Layers shall stack in order: the base lowest, then each layer above the one before it. A layer next to the base is **farther** from the observer than a layer far from the base.
- **R10 (ubiquitous):** Z-order happens **by layer** (operator, 2026-10-08). Every control of a layer shall paint above every control of every layer below it, whatever their `ZOrder` values: a control whose `ZOrder` is 0 — or negative — in a higher layer is still above all the controls of the lower layers, the base's included, even one whose `ZOrder` is 209. `ZOrder` shall order only controls that share a layer and a parent. `BringToFront` and `SendToBack` therefore move a control to the top or the bottom of **its own layer** and never across layers; changing the layer a control is on is R31's job.
- **R11 (ubiquitous):** The base shall always be the lowest and shall not be re-stacked. Any other layer may be moved to any position above the base, and the order shall be saved.
- **R12 (state):** While a layer is not visible, none of its controls and none of its background shall paint, and none of its controls shall receive mouse events or keyboard focus.
- **R13 (ubiquitous):** A layer shall cover exactly the form's rectangle. It shall have no position or size of its own, shall not change the form's size, and shall scroll and resize with the base.
- **R14 (constraint):** Whatever a layer paints outside the form's rectangle, or outside the arcs of the base's rounded corners, shall be clipped — for **every** control type, including the ones that do not clip themselves at a corner today (F5). *(Measured and narrowed 2026-10-09, slice 2b. **The straight edges are delivered for every type**: 62 control types on three paint paths, none reaches past the form's edge in a layer, where 60 of the same types do in the base. **The arcs are delivered for the types that can clip themselves**: a layer's control is a top-level control of the window and is lifted to its arc exactly as the base's is, so the same 55 types stay inside it. **The seven that cannot** — `DataGrid`, `FileDropZone`, `Maps`, `TabControl`, `ToolBar`, `Viewer`, `Custom`, and a flush `TreeView`'s content — still paint past a rounded window's arc in a layer, as they do in the base: cutting arbitrary shapes at an arc needs them tessellated and clipped against the arc, which this engine does not do. Q31.)*

### 4.3 Layer properties

- **R15 (ubiquitous):** A layer shall have `Name`, `Visible` — a state that is never saved (R35, Q26; *amended 2026-10-09*) — and the form's own backdrop properties with the same meaning and ranges: `BackgroundColor`, the background gradient (enabled, start, end, direction), `BackgroundImage` with its scaling mode, and `Transparency` (Q6). A new layer shall be fully transparent, so adding one changes nothing that is drawn.
- **R16 (constraint):** A layer shall not have `CornerRadius`, and shall not have any window property (`Title`, `WindowState`, `Resizable`, the window-dock properties…). Its corners are the base's.

### 4.4 Mouse events

- **R17 (event):** When the pointer presses, releases, clicks, double-clicks, moves, enters, leaves or wheels over a point of the form, the system shall offer the event to the visible layers from the nearest to the observer down to the base, and give it to the first control that has a **painted part** at that point. *(Delivered 2026-10-09, slice 2d, as one question asked once per frame — `pointer_claim`: the highest shown layer that holds the pointer at that point. A layer holds a point where a control of it owns the pointer there — it has a handler bound to a press, which fires over its whole rectangle, or it paints something at that point: a Label with no background of its own paints its text only, so a click beside the text is not its click — or where its background is opaque (R20). Everything below the answer is shielded: its events and state changes for that frame do not reach the host (R19), and egui is given a blocker over the claimed area so the widgets below neither light, press nor take the focus. Controls of the same layer, and of layers above, are unaffected. A frameless window still moves by its face on the same rule as before. Limits, measured: the answer is settled after the frame's controls are drawn, so egui's hover highlight of a shielded widget can show for the one frame before the blocker is registered; and a layer's image background is never counted as opaque, because its pixels are not inspected — put a Panel over it to shield, as Q8b says.)*
- **R18 (event):** When a point holds no painted part of any control in a layer — the layer's own background, the empty area of a control that paints nothing there, the area around a Label's text — the event shall pass to the layer below, unless the layer's background is opaque there (R20), and from the lowest layer to the base.
- **R19 (event):** When a point lies on a painted part of a control, the event shall belong to that control: its COBOL handler runs if one is bound, and the event is **discarded** if none is. It shall not fall through to the layers below.
- **R20 (constraint):** A layer's background shall never be the target of an event: no COBOL handler runs for it. Where the background is **opaque** at a point — it paints there at full opacity, so what is below cannot be seen — an event at that point shall not pass to the layers below and shall be discarded: an opaque layer holds the focus, and everything beneath it is shielded (operator, 2026-10-08). Where the background is transparent or translucent at a point, the event passes on as R18 says (Q8b). A control of the layer, painted above its background, still receives its own events (R19).

### 4.5 Layout

- **R21 (constraint):** Only the base shall have layout behaviour: `Dock`, `Anchor` and the flex, grid and flow layouts of spec 056. A control in a layer shall keep its designed `X`, `Y`, `Width` and `Height`, and the inspector shall not offer it `Dock`, `Anchor` or the layout modes; `X`, `Y`, `Width` and `Height` stay editable. *(Clarified 2026-10-09: "those properties" used to be ambiguous between the two groups; a control with no position could not be placed. Delivered in slice 2c: the layout engine leaves a layer's controls — and what is inside a container in a layer — out of the tree altogether, so they take no room from the base's docks, move with none of its anchors, scale their text with no layout, and never raise the form's smallest size (R13). A control that names a layer the form does not define is drawn with the base (R40) but also keeps its designed rectangle: it is not docked into a layout it was never designed for.)* When a control is moved from the base to a layer, its `Dock` shall become `None` and its `Anchor` the default; undoing the move shall give them back (Q7).
- **R22 (constraint):** The form-level window properties (`DockToOpener` and the rest of spec 037) shall stay on the form, and a layer shall not have them (R16).

### 4.6 Designer

- **R23 (ubiquitous):** The designer shall show, at all times, a **tab bar directly under the form canvas**: the fixed `Non-Visuals` tab at the far left (R46), then the base's tab, named `Form` — its name, so it reads `Form` in every IDE language, like the `Layer` property value it stands for — and not movable, then one tab per layer in stack order, left to right from the layer nearest the base. After the last tab sits a `+` that adds a layer. A form with no layers shows the `Non-Visuals` tab, the `Form` tab and the `+`. The bar has a fixed height; when its tabs do not fit, **◀ ▶ arrows at its right edge** scroll it, and it shall not make the window larger.
- **R24 (event):** When the developer selects a tab, that layer shall become **active** and the Properties inspector shall show that layer's properties, as it does the form's when the form is selected.
- **R25 (event):** When the developer clicks the visibility checkbox on a layer tab, the layer's `Visible` shall toggle and the canvas shall show or hide that layer's controls at once. The checkbox shows and sets the layer's `Visible` and nothing else — it does not change the active tab (R62). **That state is a temporary aid for editing: it is never saved and the form is not marked modified by it, and it is not an undo step** (operator, 2026-10-09: "the visibility property is meant to be used in the runtime and to temporarily edit the form in the designer"; R35, Q26). *(Rewritten 2026-10-09. It used to make the box the value the program starts with — the 2026-10-08 ruling of Q2, reversed — and to keep the active layer drawn when its box was off; selecting a layer now turns its box on (R60), so that exception is gone — Q2b.)* The `Form` tab has no checkbox: the base is always visible.
- **R26 (event):** The developer shall be able to add a layer (the `+`), delete it (the red X on its tab), rename it and re-stack it from the tab bar. A layer is re-stacked by **dragging its tab and dropping it** at another position among the layer tabs (operator, 2026-10-08). The `Non-Visuals` and `Form` tabs are the fixed ones: neither can be dragged, and no layer tab can be dropped to the left of `Form`. The gesture for renaming is not in the screenshot (Q1).
- **R27 (event):** When the developer deletes a layer, the system shall first ask for confirmation in a modal window, and the deletion, what it takes with it and its undo are R63, R64 and R65. *(Rewritten 2026-10-09. It used to ask only when the layer held controls, and to keep their handler code in the form's recycle bin; the operator's rules 5 and 6 of 2026-10-09 replace both — Q28.)*
- **R28 (event):** When the developer places a new control from the toolbox — by a click or by a drop — it shall be created in the **active tab**: on `Form` or in the active layer for a visual control, and on `Non-Visuals` for a non-visual one, which R59 has made active at the press (R48). *(Rewritten twice on 2026-10-09. The second answer, to Q25, restored "in the active layer": a visual press no longer selects `Form`; while `Non-Visuals` is active the visual entries are disabled instead — R59, R58.)*
- **R29 (state):** While a layer — or the `Non-Visuals` tab — is active, what the pointer and Select All can reach is limited to that tab's controls (R44, R45).
- **R30 (state):** While any tab other than `Form` is active — a layer, or `Non-Visuals` — the form shall not be resizable in the designer: no resize grips on the form, and `Width` and `Height` not editable. Resizing shall be possible only while the base is active.
- **R31 (event):** The developer shall be able to move the selected controls to another layer from the inspector (`Layer`) or the context menu, as one undo step.
- **R32 (ubiquitous):** Every layer operation — add, rename, delete, re-stack, move controls, change a layer property — shall be undoable and redoable. Showing or hiding a layer, and selecting a tab, are **not** operations in this sense: they change no saved state, so they are no undo step and do not mark the form modified (R25, R61; *amended 2026-10-09*).

### 4.7 Run time

- **R33 (ubiquitous):** A program shall be able to read and write a layer's properties by name, the way it does a control's: `LAYER-NAME::Visible`, `Transparency`, `BackgroundColor`, the gradient properties, `BackgroundImage` and its mode. *(Delivered 2026-10-09, slice 3. A layer is an object of class `Layer`, seeded by the host under its name with `cobolt_forms::model::LAYER_PROPS` — `Name` (read only), `Visible`, `Transparency`, `BackgroundColor`, `BackgroundGradientEnabled`/`StartColor`/`EndColor`/`Direction`, `BackgroundImage`, `BackgroundImageMode` — in the names a control's own backdrop properties carry. A write by `MOVE`/`SET`, `CALL "COBOL-SET-PROPERTY"` or `INVOKE … "SetProperty"` is accepted for every property but `Name`; anything else, and any method, is refused as a runtime error that names what a layer has, never silently ignored. No parser change was needed: `::` already reaches any seeded object.)*
- **R34 (event):** When a program writes a layer property, the next frame shall show the new state.
- **R35 (ubiquitous):** **Every layer shall start hidden** in a running form, in every host. A program shows one with `SET LAY-NAME::Visible TO TRUE`, and it **stays visible until the program hides it**; reading `Visible` before any write gives false. The `Visible` a designer was left with is **never saved**: a save writes every layer hidden — in the file, by writing no `Visible` at all — so a form saved after the developer browsed its layers starts the same as one saved before (operator, 2026-10-09; Q26). *(Rewritten 2026-10-09: it used to say "in the state it was designed in".)*
- **R36 (ubiquitous):** Layers shall behave the same in every host that runs a form: `rcrun run-form`, a form embedded as a child, and the compiled binary. *(Delivered and measured 2026-10-09, slice 3: one COBOL program — `SET LAYER-1::Visible TO TRUE`, `MOVE … TO LAYER-1::BackgroundColor`, `MOVE 40 TO LAYER-2::Transparency`, a read of `LAYER-1::Visible` into a Label, a hide, a show, and an unrelated event — gives the same eight readings under `rcrun run-form`, as an embedded child in a shell's ContentPane, and in a built binary compiled from this checkout (`cobolt-cli/tests/layers_hosts_091.rs`). All three hosts build their state with one function, `cobolt_form_host::state::initial_state`, which is what makes "every layer starts hidden" one rule rather than three.)*
- **R37 (ubiquitous):** A reference to a layer name or a layer property that does not exist shall be reported at build time, as an unknown control is. *(Delivered 2026-10-09, slice 3, at the same two gates as an unknown control: Build, and Run Form. `LAYER-9::Visible` is "this form has no control or object named", `LAYER-1::Colour` is "not a property of a layer" with the list a layer has, and `Non-Visuals::Visible` fails as an unknown reference (R55). IDE Check and the plugin `check` do not run the receiver check for any object today; that is the operator's to change, for every project at once. Accepted by the operator, 2026-10-09: IDE Check stays as it is for layers, and Build and Run Form are the gates; the Guide says so in §7 and §23.)*
- **R38 (ubiquitous):** A control in a layer shall be addressed by its name exactly as a control in the base is. `MY-BOX::Text` shall not depend on the layer `MY-BOX` is in.

### 4.8 Persistence and tooling

- **R39 (ubiquitous):** The `.cfrm` shall record the layers in stack order with their properties **other than `Visible`** (R35), and each control's layer. A form with no layers shall write none of it (R2).
- **R40 (event):** When a `.cfrm` names a layer that it does not define, the control shall be kept, shown in the base, and the problem reported in the Output panel. Nothing shall be deleted.
- **R41 (ubiquitous):** The generated-COBOL contract shall hold: the developer banner, regeneration on Build, Run, Debug and Check, English identifiers, and no change to the generated code of a form without layers.
- **R42 (ubiquitous):** A form with layers loaded into a shell's ContentPane shall behave as in a window: its layers cover the pane area the form occupies. *(Delivered 2026-10-09, slice 3: the pane's engine backdrop carries the form's layers, so each is painted over the pane's backdrop extent, as the base's own background is.)*

### 4.9 Designer — the active layer (added 2026-10-08)

- **R43 (state):** Exactly one tab is **active** at any time — the `Form` tab when the base is active. The active tab shall be drawn with a **blue face and white text**; every other tab shall be drawn with a **white face and blue text**. The colours are the same on every IDE theme.
- **R44 (state):** While a layer is active — or the base, or the `Non-Visuals` tab — every pointer interaction on the canvas shall be limited to the controls of that tab: click, Ctrl-click, drag to move, resize handles, double-click, context menu, hover feedback and the **rubber-band lasso**. The controls of every other layer are **inactive**. They are drawn, when their layer is visible, but the pointer treats them as absent: a press on one is a press on empty canvas and starts a lasso, an inactive control never blocks an active one beneath it, and a lasso selects only the active layer's controls, however many others its rectangle covers. This holds when the base is the active layer too. When the active layer changes, controls that are not in the new active layer shall leave the selection; so shall controls moved to another layer (R31).
- **R45 (event):** When the developer presses Cmd+A on macOS or Ctrl+A elsewhere, and no text field has focus, the designer shall select every control of the active layer — the base's, when the base is active — and **no** control of any other layer. It selects the same set as today's Select All (F10), restricted to the active layer; when that layer holds no controls, the selection becomes empty.

### 4.11 The `Non-Visuals` tab (added 2026-10-08)

- **R46 (ubiquitous):** The designer shall show a fixed **`Non-Visuals` tab** as the first tab of the bar, to the left of `Form`, on every form — with or without layers, with or without non-visual controls. It shall have no visibility checkbox and no red X, and it cannot be renamed, deleted, hidden, dragged or re-stacked. It shall stay in view when the bar scrolls (Q21). It is drawn in the colours of R43: blue face and white text while active, white face and blue text otherwise. Its label is a translated IDE string, not an identifier (Q14).
- **R47 (ubiquitous):** The tab shall hold **every** control for which the catalogue's own predicate `ControlType::is_non_visual()` is true, and no other control. Today that is `Timer`, `AgentObject`, `KnowledgeBase`, `RestClient`, `SqlDatabase`, `IndexedFile`, `WebSearch`, `Snackbar` and the AWS controls (F11); a type added to the predicate later lands in the tab with no change here. A non-visual control belongs to no layer and is not on the `Form` tab: the inspector shall not offer it `Layer` (R3) and the `.cfrm` shall not record one (R39). Its name is still drawn from the one namespace (R4). `MenuBar`, `SideMenu` and `StatusBar` stay on the base (Q4).
- **R48 (event):** When the developer starts dragging a non-visual control out of the toolbox, the `Non-Visuals` tab shall become active, so that the grid is on screen when the control is dropped (Q22). The same shall happen when a non-visual control is pasted or duplicated. Where on the canvas the control is dropped does not matter: the grid decides its cell (R49). *(Extended 2026-10-09: R59 moves the switch from the start of the drag to the press on the toolbox control, so a click that places the control at the centre of the canvas selects the tab too.)*
- **R49 (ubiquitous):** The tab shall lay its controls out in a **grid of 5 columns and as many rows as needed**, filled row by row, left to right then top to bottom, from the top-left corner of the canvas. Each control shall have **its own cell** — its icon and label fill the cell, as the screenshot's cards do — and no two controls share one. When the rows do not fit the visible canvas, the tab shall scroll vertically; the form and the window do not grow (Q16).
- **R50 (ubiquitous):** The order of the cells shall keep **controls of the same type together**: the types in A–Z order, case-insensitive, by the type's English name (so the arrangement is the same in every IDE language — Q19), and within a type the controls in A–Z order by control name, case-insensitive (Q18).
- **R51 (event):** When anything that can change the order happens — a control is added, deleted, renamed, pasted, duplicated, or one of those is undone or redone, or the form is loaded — the system shall arrange the whole grid again. It leaves no empty cell between controls: deleting one moves the ones after it up. The arrangement is derived from the controls' types and names alone and stores nothing (Q12).
- **R52 (event):** The developer shall be able to select a card with a click, with Ctrl-click and with the rubber-band lasso, and to select all of them with Cmd+A / Ctrl+A (R44, R45). Dragging a card shall **not** move it to another cell: the grid decides. A card shows the inspector of its control, with Properties, Events and Procs as for any other control.
- **R53 (event):** When one or more cards are selected and the developer presses **Delete** (or Backspace, as today), or chooses **Delete** from the context menu opened with the right button, the system shall remove the controls **by the same path as any control**: the cascade, the confirmation when a control carries event code, the recycle bin that keeps the control and its code (always, as `DeleteControl` does today), and one undo step (F13; *corrected 2026-10-09: this said "when the developer asks for it", a choice that does not exist*). The control's own handler code goes with it; a procedure that only mentions the control is **kept** and reported in the Output panel, never deleted (GOLDEN RULE: user code is sacred). Nothing else is needed — no tab-specific button.
- **R54 (event):** When a form that already holds non-visual controls is opened, the system shall place them in the grid by R49 and R50 with no action from the developer. Nothing in the `.cfrm` changes: the controls keep their `X` and `Y`, a form opened and saved without an edit is byte-identical (R2), and no control is deleted or re-homed (Q17).
- **R55 (ubiquitous):** The tab shall be a design-time surface only. Non-visual controls paint nothing in a running form, as they never have (F12), so the tab changes nothing at run time in any host: `rcrun run-form`, a child form, the compiled binary. A program cannot address the tab: `Non-Visuals` is not a layer, so `Non-Visuals::Visible` is an unknown reference and fails the build as R37 says.
- **R56 (state):** Exactly one tab is active (R43). When `Non-Visuals` is active, `Form` and every layer tab show the inactive colours, and the canvas shows the grid and nothing else, as the screenshot does: the controls of the base and of the layers are not drawn, so the cards are not hidden behind them (Q24).
- **R57 (state):** While `Non-Visuals` is active, the form shall not be resizable in the designer (R30).
- **R58 (event):** A **visual** control cannot be created in, moved to or pasted into the `Non-Visuals` tab. While that tab is active the toolbox's visual entries are disabled (R59), and a **paste is disabled when the clipboard holds any visual control** — all or nothing (Q29). A visual control that reaches the canvas some other way while the tab is active is refused with a message in the Output panel, and is never rerouted to another tab. The `Layer` choices of R31 do not list the tab (Q15). *(Rewritten twice on 2026-10-09: first to select `Form`, then, by the operator's answer to Q25, to disable and refuse.)*

### 4.12 Choosing the tab, and deleting a layer (added 2026-10-09)

Six rules from the operator, 2026-10-09, with the same tab bar in the screenshot: `Non-Visuals` (active, blue) · `Form` · `Layer 1` ☒ ✕ · `Layer 2` ☒ ✕ · `+`. The operator's answers to Q25 and Q26 the same day rewrote R25, R28, R35, R58, R59 and R61 (each says so in a note) and settled Q12, Q18, Q24 as the defaults.

- **R59 (event):** When the developer presses on a control in the toolbox — to click it or to start dragging it — the designer shall make **`Non-Visuals`** the active tab if the control is non-visual (`ControlType::is_non_visual()`, R47), from any tab it was on. The switch happens at the press, before the control is placed, so the tab that receives it is on screen when it appears (operator, 2026-10-09, rule 1; Q22). A **visual** control leaves the active tab as it is and is created in it (R28) — **except while `Non-Visuals` is active, when every visual entry of the toolbox is disabled**: drawn greyed, it takes no press, no click and no drag, so the developer chooses `Form` or a layer first. The toolbox is fully active only while `Form` or a layer is the active tab (operator, 2026-10-09, answer to Q25). A user control counts as visual. Selecting `Non-Visuals` this way changes no layer's `Visible` (R61). *(Rewritten 2026-10-09: the first draft sent every visual press to `Form`.)*
- **R60 (event):** When the developer selects a layer tab, the designer shall draw the **`Form` first and the selected layer on top of it**: the base is always drawn, and the selected layer is drawn above it (R9, R25). If that layer's `Visible` is off, selecting it shall turn it **on** (operator, 2026-10-09, rule 2). The controls of the base stay inactive while a layer is active, as R44 already says.
- **R61 (event):** Because one layer is edited at a time, when the developer selects a layer tab the system shall also turn `Visible` **off** on every **other layer**. The base is not a layer and is never hidden. It does this **only at the selection**: afterwards the developer may check any layer's box, and the system shall not turn it off again until another layer tab is selected (operator, 2026-10-09, rule 3). Selecting `Non-Visuals` or `Form` hides nothing. These changes are to the in-memory `Visible` of R25, which is never saved and is no edit: the form is not marked modified, no undo step is made (R32), and a form saved after the developer has browsed its layers starts at run time exactly as before — every layer hidden (R35, Q26; operator, 2026-10-09). *(Rewritten 2026-10-09: the first draft made these writes to the saved property.)*
- **R62 (event):** When the developer checks or unchecks the visibility box on a layer tab, only that layer's `Visible` shall change. **The active tab does not change**: whatever tab was selected stays selected, whether the box belongs to the active layer's own tab or to another (operator, 2026-10-09, rule 4). A layer whose box is off is not drawn (R12) even while it is the active one, and its controls cannot be reached (Q2b).
- **R63 (event):** When the developer clicks the red ✕ on a layer tab, the designer shall first **select that layer's tab** as R60 and R61 describe, and then open a **modal confirmation window** — **whether or not the layer holds controls** — that names the layer and says how many controls and how many event handlers would be deleted with it. Nothing is deleted until the developer confirms; cancelling leaves the layer where it was, its tab active (operator, 2026-10-09, rule 5; Q27). The window is modal, shows nothing but the question and its buttons, and **never changes its own size** (§6).
- **R64 (event):** When the developer confirms, the system shall delete the **layer**, **every control on it** — a container's children included (R8) — and **every COBOL event handler bound to those controls** (operator, 2026-10-09, rule 6). A procedure that is not bound to one of them and only mentions it is **kept** and reported in the Output panel, never deleted (GOLDEN RULE: user code is sacred; R53). A layer has no event handler of its own (Q9). Afterwards `Form` is the active tab (Q27).
- **R65 (event):** The whole deletion shall be **one undo step**, and redo shall repeat it. Undo shall bring back the layer with its name, properties and position in the stack, every control with its name, properties, `ZOrder` and container link, and every event handler, exactly as they were (operator, 2026-10-09, rule 6; R32). Every control leaves through the path a single control takes — the form's recycle bin, always — so the confirmation offers no further choice (Q28).

## 6. Constraints & steering check

- **i18n (6 languages):** yes. Tab bar, tooltips, the `Non-Visuals` tab's label and tooltip, the add/rename/delete/re-stack commands, the delete confirmation, the inspector labels and every message above are `Tr` fields in all six languages. `Layer-1` and the property names stay English.
- **Generated code:** a form with layers regenerates on Build/Run/Debug/Check; a form without them generates what it generated before. Layer names are COBOL identifiers and stay English. The goldens in `crates/cobolt-codegen/tests/golden/` (five `.cbl` files and the `corpus/` of PowerChat and PowerDemo3) pin both; `UPDATE_GOLDEN` is never run for this feature. *(Corrected 2026-10-09: this said `tests/golden/`, which does not exist.)*
- **System KB:** the `Layer` property, the layer properties and the `layer::Property` syntax enter the `cobolt-compiler` property/method/event doc tables in the same change; `cargo run -p cobolt-ide --example build_chunked_kb` regenerates `assets/knowledge/chunked.data`; `prebuilt_chunked_kb_matches_the_published_documentation` must be green.
- **Docs:** `docs/developers-guide-en.md` gains a Layers section and a Non-Visuals section, written for a PowerCOBOL or isCOBOL developer, in COBOL and prose only, with screenshot placeholders; its five translations are deleted in the same change (GOLDEN RULE #8).
- **Interpreter parity:** `rcrun run-form`, embedded child forms and the compiled binary (`run_form_app`) all change for the layers; read the `interpreter-binary-parity` skill first. The `Non-Visuals` tab changes none of them: it is a design-time arrangement (R55).
- **Rounded corners:** R14 sits on spec 057; read the `rounded-corners` skill first.
- **Windows never resize themselves:** the tab bar has a fixed height and scrolls (R23), and the designer window does not change size when the 64th tab arrives. The delete-layer confirmation (R63) is a modal window that owns an explicit size, `.resizable(false).fixed_size(...)`, lays its text out from that stored number — never from `available_width()` or `max_rect()` — and wraps inside it; a long layer name or a long translation changes the text, never the window. `panels/leaderboard_modal.rs` is the reference (CONVENTIONS.md, `egui-resize-guardian`). The `Non-Visuals` grid scrolls inside the canvas when it has more rows than fit (R49); it never grows the form or the window.
- **Contrast:** the active and inactive tab colours (R43) are fixed, not read from the IDE theme, since the IDE ships 33 themes and glass ones render dark-on-dark (CLAUDE.md, chat-UI rule). The plan checks that the checkbox and the red X read on both faces.
- **User code is sacred:** deleting a layer deletes its controls' **own** handler code — only after an explicit confirmation naming how many handlers go, and as one undo step that brings all of it back (R63–R65; operator, 2026-10-09; Q28). That is the case the rule allows: a control deleted together with its own handlers. A procedure that merely mentions one of them stays, reported (R64). A bad `.cfrm` is reported, never repaired by deleting (R5, R40). Deleting a non-visual control takes its **own** handler code and nothing else; a procedure that merely mentions it stays, reported (R53).
- **Fix vs feature:** feature. Branch `features`. That branch is checked out in another worktree and is 200 commits behind `main`, so work goes on a per-change branch off `main` — `features-form-layers`, created for this spec — and lands with `git push origin HEAD:features` (`structure.md`). The push obeys GOLDEN RULE #1.
- **Version:** `z` bump from 1.90.21 and a `CHANGELOG.md` entry.
- **Forum:** no announcement unless the operator asks (GOLDEN RULE #4b).

## 7. Open questions

Each carries the default this spec assumes.

- **Q1 — What the screenshot leaves open.** (a) Resolved 2026-10-08: layers are re-stacked by dragging and dropping their tabs; the `Non-Visuals` and `Form` tabs are the fixed ones (R26). (b) How a layer is renamed: double-click on its tab is assumed. (c) The checkbox draws as a boxed X; this spec reads boxed X as checked, so visible. (d) Resolved 2026-10-08: the base is named `Form`, and no layer may take that name (R6). (e) The screenshot's tabs read `Layer 1` and `Layer 2`, with a space; a name a program writes as `LAYER-1::Visible` cannot hold one. The spec names new layers `Layer-1`, `Layer-2` (R6). Should the tab show the name as is, or a spaced label for it?
- **Q2 — Resolved 2026-10-08, reversed by the operator on 2026-10-09.** The first ruling made the checkbox the layer's `Visible` property and the value the program starts with. The second: the property is "meant to be used in the runtime and to temporarily edit the form in the designer", it is never saved, and every layer starts hidden — see R25, R35 and Q26.
- **Q2b — Resolved by the operator, 2026-10-09, with one residue.** Selecting a layer turns its box on (R60), so the designer no longer needs to draw an active layer whose box is off. What is left: a developer who then **unchecks the active layer's own box**. Default (R62): the layer is hidden at once and stays active, and its controls cannot be reached (R12); the developer checks the box to edit it again. The alternative keeps drawing the active layer whatever its box says.
- **Q3 — Resolved by the operator, 2026-10-08.** The controls of the other layers are inactive while one layer is active, for every mouse event including the lasso (R44), and Select All reaches only the active layer (R45).
- **Q4 — What may live in a layer.** Partly resolved by the operator, 2026-10-08: the non-visual controls live in the `Non-Visuals` tab, not in the base and not in a layer (R47). Default for the rest: `MenuBar`, `SideMenu` and `StatusBar`, which are window chrome, belong to the base only. Every other control type may live in a layer.
- **Q5 — The limit of 64.** Default: 64 layers **above** the base, so 65 tabs with the `Form` tab. If 64 includes the base, change R7 to 63.
- **Q6 — `Transparency`.** Default: as on a form, it fades the layer's **backdrop**; the controls keep their own `Transparency`. The alternative, as on a `Panel`, fades the controls too.
- **Q7 — "Dock behaviour" (rule 6).** Default reading: the per-control `Dock`, `Anchor` and layout modes of spec 056, and the form-level window dock. If rule 6 meant only one of them, R21/R22 narrow.
- **Q8 — Resolved by the operator, 2026-10-08.** An opaque layer background does not let clicks through: opaque means focus on that layer, and what is below it is shielded (R20). The background still handles no event of its own.
- **Q8b — Left over from Q8: how opaque is "opaque"?** Default: fully opaque at the point — `Transparency` 0 and a colour, gradient or image pixel with full alpha there. A background with any transparency lets events through, so a dimming scrim that must also block clicks needs a `Panel` over the layer, as the `SCRIM` Panel in the screenshot is today. If any visible fill should block, R20 changes to "paints anything".
- **Q9 — More from COBOL.** Not in this spec: re-stacking a layer at run time, a layer `Enabled`, layer events. Add any of them?
- **Q10 — Keyboard focus.** Default: Tab walks the base first, then each layer from the lowest up; hidden layers are skipped, and so are the controls shielded by an opaque layer background (R20), which cannot be seen or clicked.
- **Q11 — A control's `Layer` at run time.** Default: readable, not writable. The alternative lets a program move a control to another layer.

The questions below come from the `Non-Visuals` tab (R46–R58). Each carries the default the requirements above assume.

- **Q12 — Derived or stored arrangement.** Default: **derived** — the grid is computed from the controls' types and names every time and nothing is written to the `.cfrm`, so a form opened and saved without an edit is byte-identical (R2, R54), and a control's cell changes when it is renamed or another is added. The alternative stores a cell, or rewrites `X`/`Y` to the cell's position, which keeps a card where it was but makes saving a form change its file and lets two cards claim one cell.
- **Q13 — A non-visual control's `X`, `Y`, `Width` and `Height`.** With the grid deciding the cell (R49), these four properties no longer place or size anything, and the designer already ignores them for layout (F12). Default: the inspector does not offer them for a non-visual control, as R21 does for a control in a layer. The `.cfrm` keeps the values it has (R54).
- **Q14 — The tab's label.** Default: a translated IDE string in all six languages (`Non-Visuals` in English), because it names no property or control a program can address. The alternative is the fixed English word, as `Form` is.
- **Q15 — Resolved by the operator, 2026-10-09 (answer to Q25).** A visual control is **not** created while `Non-Visuals` is active: the toolbox's visual entries are disabled (R59) and a paste holding a visual control is disabled (R58, Q29). So the "go back to the previous tab" default and the "send it to `Form`" reading are both dropped; the alternative that survives is refusal, and it is not a message at the drop but a disabled entry before it.
- **Q16 — "As many lines as needed."** Default: the tab scrolls vertically when the rows do not fit, as the base does; the form and the window never grow (R49).
- **Q17 — A non-visual control inside a container.** A `.cfrm` can hold one whose `parent` is a `Panel`. Default: the tab shows it like any other and the file is not touched, so the `parent` stays and a cascade delete of the container still takes it (F15); a new non-visual control is created with no container parent, since the grid spans the form. The alternative re-homes them to the form on load, which changes the file.
- **Q18 — "A–Z order" inside a type.** Default: plain, case-insensitive, by control name, so `TMR-10` comes before `TMR-2`. The alternative is natural order, with digit runs compared as numbers. Note: a card's label is what it shows today (`nv_card`) — the screenshot's `llama3.2` is a model name, not a control name — and the order follows the **control name**, so cards with different labels may not look sorted.
- **Q19 — "Same type" and its A–Z.** Default: the type's English name (`AgentObject`, `IndexedFile`, `KnowledgeBase`, `RestClient`, `Snackbar`, `SqlDatabase`, `Timer`, `WebSearch`, then the AWS controls by theirs), so the arrangement does not depend on the IDE language. The alternative sorts by the toolbox label, which is translated and would reorder the grid when the IDE language changes.
- **Q20 — `Snackbar`.** The catalogue lists it as non-visual (F11), though a snackbar does appear at run time when a program shows one; its designer card is a design affordance like the rest. Default: it lives in the `Non-Visuals` tab, as the catalogue says.
- **Q21 — "Fixed" tab.** Default: fixed means two things — it cannot be removed, renamed, hidden or re-stacked, and it stays pinned at the left when the ◀ ▶ arrows scroll the other tabs. The first alone would let it scroll away.
- **Q22 — Resolved by the operator, 2026-10-09, for the toolbox.** The tab is selected at the **press** on a toolbox control, which begins both a click and a drag (R59), so it is on screen before the control is placed; a click places the control at the centre of the canvas today (F16). Default for the rest, unchanged: also on paste and duplicate of a non-visual control (R48), and not on load, undo, or an edit made by the coding agent, which leave the active tab alone.
- **Q23 — Handlers on a non-visual control.** A card's events (a `Timer`'s `onTimer`, an `AgentObject`'s) open the same editors as any control. Default: unchanged; the spec adds nothing.
- **Q24 — What the canvas shows besides the grid.** Default (R56): nothing — the screenshot shows only the cards. The alternative keeps the base and the visible layers drawn, dimmed, behind the cards.

The questions below come from the operator's six rules of 2026-10-09 (R59–R65). Each carries the default the requirements above assume.

- **Q25 — Resolved by the operator, 2026-10-09.** A visual press from `Form` or a layer **stays on that tab** and creates the control there; **while `Non-Visuals` is active every visual toolbox entry is disabled, and so is pasting a control that is not non-visual**; the toolbox is fully active only while `Form` or a layer is selected (R28, R58, R59). The first reading — every visual press goes to `Form`, so no toolbox control could ever land in a layer — is dropped.
- **Q26 — Resolved by the operator, 2026-10-09: design-time visibility, never saved.** `Visible` is meant for run time and for editing in the designer; every layer starts hidden at run time and stays shown once a program shows it, until a program hides it; **a save writes every layer hidden**, and `Non-Visuals` never appears at run time (R25, R35, R55, R61). Built as: the designer keeps the shown/hidden state in memory, outside the form, so selecting a tab and ticking a box mark nothing modified and make no undo step (R32); the file carries no `Visible`. This reverses Q2.
- **Q27 — Which tab after a layer goes.** R63 selects the layer, so it is the active one when it is deleted. Default (R64): `Form` becomes active, and no other layer's shown/hidden state changes, so the deletion does not run R61 a second time. Undo (R65) brings the layer back and selects it as any tab selection would (R60, R61). The alternative selects the layer below the deleted one, which would run R60 and R61 on it.
- **Q28 — Resolved by reading the code, 2026-10-09: no extra choice.** F13 said the delete confirmation carries a **Preserve in Recycle** choice. It does not: `show_delete_confirmation` offers Cancel and Delete, and every `DeleteControl` puts the control — handlers included — in the form's recycle bin, whatever the user chose. A layer's controls leave by the same command, so the code is kept in the recycle bin as for any control, and undo is the other way back (R65). The confirmation (R63) therefore offers no further choice.
- **Q29 — Paste while `Non-Visuals` is active (default).** All or nothing: the paste is disabled when the clipboard holds **any** visual control (R58). On `Form` or a layer, a clipboard that mixes the two kinds pastes the visual controls into the active tab and the non-visual ones into the `Non-Visuals` grid, and leaves the active tab as it is. The alternative pastes only the non-visual ones while `Non-Visuals` is active and drops the rest silently.
- **Q31 — The seven types that cannot clip themselves, at a rounded window's arc (accepted by the operator, 2026-10-09: the default stands; slice 2b).** R14 asked for every type. The engine delivers the straight edges for all of them and the arcs for the 55 that lift their own frame to the arc; `DataGrid`, `FileDropZone`, `Maps`, `TabControl`, `ToolBar`, `Viewer` and `Custom` (and a `TreeView` flush with the corner) paint past a rounded, see-through window's arc in a layer exactly as they already do in the base. Closing it means tessellating those controls' shapes and clipping the triangles to the arc's polygon — exact, but a new clipper that must keep premultiplied alpha, the font atlas's texture coordinates and feathering right, for a case (one of seven types reaching the corner of a title-bar-less rounded window) the base has lived with. Default: **leave it, as measured and listed above**, and open a separate fix if a project meets it. The alternative builds the clipper in this feature. *Settled 2026-10-09: the operator accepted the limitation; the Developer's Guide lists the seven types (§7 caveats, §23) and a separate fix is opened only if a project meets it.*
- **Q30 — The `+` (default).** Adding a layer selects it, so it is shown (R60) and the other layers are hidden (R61): a layer whose box starts unchecked is invisible and could not be edited. The alternative adds it unselected and unchecked, which leaves the developer to select it first.

## 8. Findings

Read on `main` at 7ff1c4f (1.90.21), 2026-10-08; F11–F15 read the same day, when the `Non-Visuals` tab was added. Line numbers rot; `/plan` re-reads each one.

- **F1 — Flat controls with a parent link.** `Form.controls: Vec<Control>` (`cobolt-forms/src/model.rs:8039`); nesting comes from `Control.parent` (`:4130`) and the `<Children>` tree is rebuilt at save. A control's layer follows the same pattern: a field on the flat control.
- **F2 — `ZOrder`.** `Control.z_order` (`:4118`) orders siblings only (spec 012 R14), which is what R10 relies on.
- **F3 — One namespace.** A control's name is `Control.id`. The designer issues free names with `next_unique_id` / `next_unique_id_reserved` (`cobolt-ide/src/panels/designer.rs:4422`, `:4439`), and COBOL reaches a control as `receiver::member` (`control_refs_in_code`, `model.rs:1725`), so a layer joins the same flat namespace.
- **F4 — The painted-part rule exists.** `window_drag_blocked` (`cobolt-forms/src/render.rs:3078`) with `face_see_through` (`:3008`), `passive_to_the_mouse` (`:3041`) and `binds_a_press` (`:3031`) already decides which parts of a Label, Panel, GroupBox and PictureBox paint and which are see-through. R18/R19 ask the same question for every mouse event. **One difference:** a press on an unbound passive control moves a frameless window today; R19 discards the event instead. `/plan` should reuse the painted-part test, not copy it.
- **F5 — Corner clipping.** `self_clipping_type` (`render.rs:969`) and `notch_mask_rounding` (`:915`). Per CLAUDE.md (as of 1.65.2) `DataGrid`, `FileDropZone`, `Maps`, `TabControl`, `ToolBar` and `Custom` do not clip themselves; R14 requires a clip for them in a layer. *(Read again 2026-10-09 at `ade11db`: `self_clipping_type` now also leaves out `Viewer`, so seven types, and `a_rounded_window_ends_at_its_arc.rs` asserts that those paint past a window's arc — R14 changes that expectation on purpose.)*
- **F6 — Two meanings of dock.** A control's `Dock`/`Anchor` and layout modes are spec 056. `DockEdge` (`model.rs:7561`) is the form-level window dock of spec 037. See Q7.
- **F7 — Form corner radius.** `Form.corner_radius` (`:8103`) rounds the window only while the title bar is hidden (`window_corner_radius`).
- **F8 — Load and save.** `load_form` (`cobolt-forms/src/xml.rs:536`) and `save_form` (`:1936`).
- **F9 — The form's backdrop fields** that R15 repeats on a layer: `background_color`, `background_gradient_*`, `transparency`, `background_image`, `bg_image_mode` (`model.rs:8022`–`8038`).
- **F10 — Select All and the lasso today.** Cmd/Ctrl+A is handled at `cobolt-ide/src/panels/designer.rs:9517` (`modifiers.command`, only while no text field has focus) and selects every id in `form.controls`, which is the flat list, so children inside containers are included. The rubber-band lasso starts from a drag on empty canvas (`:13875`) and is drawn at `:9199`. R44 and R45 narrow both to the active layer.
- **F11 — "Non-visual" has one definition.** `ControlType::is_non_visual()` (`cobolt-forms/src/model.rs:3958`): `Timer`, `AgentObject`, `KnowledgeBase`, `RestClient`, `SqlDatabase`, `IndexedFile`, `WebSearch`, `Snackbar`, and `is_aws()` (spec 078). Its doc comment reads "invisible at runtime (shown as icon boxes in designer)". The painter (`paint.rs:3442`), the renderer (`render.rs:3080`, `:6799`, `:13536`) and the layout engine already ask it rather than keep a list, after one list drifted (`WebSearch`, 2026-09-08). R47 asks it too; a hand-written list here would drift the same way.
- **F12 — Today's non-visual controls.** Each is drawn on the **designer** canvas as a glass card with a stroke icon and a label (`nv_card`, `paint.rs:2395`) at its own `rect`, and paints **nothing** in a running form (`cobolt-forms/tests/non_visual_controls_stay_in_the_designer.rs`). The layout engine already keeps them out of every layout: they take their designed rect (`layout/mod.rs:504`–`510`) and are skipped by min-size (`layout/minsize.rs:118`) and collision (`layout/collide.rs:59`, `:116`). So a cell in a grid changes where the card is drawn at design time and nothing else — the property R55 relies on.
- **F13 — The delete path R53 reuses.** `Designer::delete_selected` (`cobolt-ide/src/panels/designer.rs:4778`): `cascade_ids_for` adds the descendants of a container (`:4712`); if any control carries event code it sets `pending_delete` — a confirmation with **Cancel and Delete only** (`show_delete_confirmation`, `:9610`) — otherwise `delete_ids_now` (`:4735`). *(Corrected 2026-10-09: this line used to promise a **Preserve in Recycle** choice that does not exist. Every `Cmd::DeleteControl` calls `recycle_control` (`cobolt-forms/src/model.rs:8827`) unconditionally, which also prunes the form's `data_bindings` — and the command's reverse does not put them back, which R65 must do for a layer. `delete_ids_now` applies one `DeleteControl` per control, so a container and its children are several undo steps today; a layer deletion wraps them in one `Batch`.)* Delete and Backspace are read at `:9502`. A procedure left referencing only deleted controls is **kept** and reported through `orphan_notices` (`:4760`–`4773`), the user-code-is-sacred rule R53 repeats.
- **F14 — A non-visual card has its own size.** `style_paint` (`designer.rs:1721`) treats it apart from visual controls — "a size the designer picked for it" — and copies only its ink and size between non-visual controls. That is the `Width`/`Height` Q13 would stop offering.
- **F15 — Re-homing on a drop.** A dropped or nudged control is re-homed to the container under its body (`reparent_to_drop`, `designer.rs:4463`; `nudge_selection`). Under the grid there is no container under a card, which is why a new non-visual control is created with no container parent (Q17).
- **F16 — A toolbox click places the control at once, at the centre.** Read 2026-10-09 on `main` at 2c30953. A click on a control in the toolbox returns its type (`cobolt-ide/src/panels/toolbox.rs:877`, "Click still places at center (legacy)"), and `app.rs:19685`–`19690` adds it to the designer at the middle of the form (`add_control(ct, cx, cy)`). A drag takes another path: the **press** stores the type as the drag-and-drop payload (`toolbox.rs:860`–`866`, `pressed_to_drag`), and `DesignerPanel::handle_toolbox_dnd` places it where it is released. Both begin with the same press, which is why R59 hangs the tab switch on the press. `/plan` re-reads these lines; `toolbox.rs:697`–`702` is the same pair for a user control (`dragged_user_control`), whose type R59 has to classify as visual or not.

# Spec — builds share one compiled-crate cache

- **Status:** implemented in 1.91.160 (operator, 2026-10-15: Q1 = a fix; Q4 = yes; the stale-platform rule added)
- **Folder:** specs/101-shared-build-cache/
- **Author:** operator question, written by Claude   **Date:** 2026-10-15
- **Branch:** `fixes` (Q1, settled). A fix gets no spec folder as a rule; this one stays as the design record because the operator asked for the spec and the plan.

## 1. Overview
The operator: *"can the build identify project crates sources that were not updated between powerrustcobol versions, so it would be compiled just once (when the object file does not exist; if it is removed or the crate changes, then the compiler would turn the .rs into rust object format)? This has the potential to accelerate the builds."*

Cargo already has that rule: a crate is compiled to an `.rlib` once and compiled again only when its source, features, profile or toolchain change. What PowerRustCOBOL does not do is let two programs *share* the result, and its full build throws the result away. Facts, read in the source and measured on 2026-10-15 (macOS, cargo and rustc 1.95.0):

1. **One private `target/` per program.** `build_core` (`cobolt-compiler/src/lib.rs`) runs `cargo build [--release] --message-format=json --offline` inside `<build folder>/cobolt-build-<name>` with `CARGO_TARGET_DIR=<that folder>/target`. The three programs staged on this machine hold 1.4 GB, 1.4 GB and 2.6 GB.
2. **What is in one.** PowerDemo3's finished release build has 499 `.rlib` files; 12 are ours (`cobolt_*`, 59 MB of 695 MB), the rest are third-party (egui, eframe, serde …) that no PowerRustCOBOL version can change. The generated manifest names the platform crates by `path =` and the rest from the registry, with no `[profile]` of its own.
3. **Sharing works.** Two throwaway programs that depend on `cobolt-ast` the way the generated project does, each in its own target folder: 30 crates compiled for each. Both in one shared folder: 30 for the first, **1** for the second (itself). The path crates and the registry crates were both reused.
4. **Cargo judges our crates by modification time, not content.** Touching `cobolt-ast/src/lib.rs` with no change to its bytes made cargo compile it again. And a source older than the last compile is believed fresh: a path crate whose code was changed, with a 2020 modification time, was not compiled again and the program still ran the old code. So an SDK restored from an older copy would be linked stale.
5. **A full build discards everything.** `opts.full` moves the whole staging folder aside (`discard_dir`): sources, `Cargo.lock` and `target/`. The IDE's Build button is a full build whenever the project's recorded version is missing or older (`build_needs_full`), so after each upgrade every program recompiles its ~500 crates, third-party included.
6. **Programs do not agree on versions.** Nothing seeds a program's `Cargo.lock`; each is resolved offline from the registry cache of the day. Two form programs on this machine already differ on `aes` (0.9.2 / 0.9.3), `inout` (0.2.3 / 0.2.2) and `json5` (1.3.2 / 1.3.1). A crate of another version is another compiled unit, and so is everything that depends on it, so a shared folder would hit far less than in (3).
7. **A past incident constrains the design.** `discard_dir` renames the folder aside because a delete that walks a tree cargo is writing leaves fingerprints vouching for deleted files and the next build dies with "no such file" against crates nobody touched (operator report, 2026-09-15). A shared folder is a tree several builds use at once.
8. **The tests assume a private folder.** `remove_build_staging` removes one staged program's ~1 GB `target/`; `HEAVY_BUILD` serialises real builds to bound the disk.

9. **Found while planning (2026-10-15).** (a) Seeding a new program's lock with the repository's `Cargo.lock` is accepted offline and pins `serde` to the SDK's 1.0.228 (a lock of 280 packages, against 262 resolved fresh). (b) A lock that pins a version whose `.crate` was never downloaded fails offline with "failed to select a version" and **without** the word `--offline`, so `build_core`'s existing cold-cache retry (`captured.contains("--offline")`) does not fire for it. (c) `cargo clean -p <crate>` removes **every** compiled variant of that crate from a shared cache (two feature variants: 2 → 0) and touches no other crate; naming a crate outside the graph is an error. (d) A second build on a held cache prints `Blocking waiting for file lock on artifact directory` (cargo 1.95). (e) `sha2` is already a dependency of `cobolt-compiler`, and the fourteen SDK crates are 18 MB of source. (f) `cargo clean -p <crate>` works from a program's own staging folder for exactly the crates listed in that program's `Cargo.lock` (a console program matched 8 of the 14, a forms program 12) and fails with "did not match any packages" for the others. Run in a *shipped* SDK, whose workspace is trimmed but whose lock is the full 1,046 packages, `--locked` is refused ("cannot update the lock file") and without it cargo rewrites the SDK's own `Cargo.lock` (914 packages), so cleaning is done from the program's folder, which the build owns.

*Not measured:* the wall-clock of a cold versus a warm forms program (AC12 will), and Windows and Linux (only macOS was run).

## 2. Goals / Non-goals
- **Goals:** third-party crates compiled once per machine, toolchain, profile and feature set — not once per program; the platform crates and the program compiled again when, and only when, they changed; the "nothing compiled by an older PowerRustCOBOL survives" guarantee kept for what can be stale; less disk.
- **Non-goals:** content-hash freshness for unchanged-but-retouched sources (`sccache`, or installing the SDK so unchanged files keep their times) — a later step; prebuilt `.rlib` files shipped with the IDE (bound to the exact `rustc` and target); pruning old variants or a "clear cache" button; any change to the release profile (`opt-level`, LTO), which trades build time against the speed of the built program and is a separate decision; the stale-build prompt and the `built_with_version` stamp; a cache per project or shared between machines.

## 3. Requirements (EARS)
- **R1 (ubiquitous):** All programs built on one machine shall keep their compiled crates in one cache, in the build folder (spec 100) beside the programs' staging folders, with one area per profile (debug, release) as cargo keeps them.
- **R2 (event):** When a build needs a crate the cache already holds, compiled from the same source with the same features, profile and toolchain, by this program or another, it shall use it and shall not compile it again.
- **R3 (event):** When a crate is missing from the cache, or its source, its features or the toolchain changed, the build shall compile it and the crates that depend on it.
- **R4 (ubiquitous):** A program staged for the first time, or after a full build, shall start from the dependency versions the SDK was tested with (the `Cargo.lock` the SDK ships), so two programs resolve the same version of every third-party crate they share. Where the local registry cache cannot supply a pinned version the build shall drop the seed and resolve as it does today, offline first. A program that already has a lock keeps it until its next full build.
- **R5 (ubiquitous):** A full build shall discard the program's staging folder as today, shall compile the platform crates and the program again from their sources, and shall leave third-party crates in the cache.
- **R6 (ubiquitous):** A platform crate shall never be linked from code compiled from a source that differs from the one now on disk, whatever the files' modification times say, an SDK restored from an older copy included. While file times are truthful (the files are newer than the cache's record of them), cargo's own rule applies and only the crates that changed, and what depends on them, are rebuilt.
- **R15 (event, operator, 2026-10-15):** When any platform crate in the shared cache is stale — its source differs from what the cache last compiled while its files do not look newer, so cargo would believe the old code — the build shall be a full build (R5), whatever was asked for, and the log shall name the stale crates and say so.
- **R7 (constraint):** No build shall delete files from inside the shared cache by walking it. What the cache must forget, it forgets through cargo, which holds the cache's lock.
- **R8 (state):** While another build holds the cache, a build shall wait and say in its log, in plain words, that it is waiting for another build; waiting shall not fail it. (Cargo's own line is `Blocking waiting for file lock …`.)
- **R9 (ubiquitous):** The binary a build installs shall be the one that build produced; building one program shall never change the binary installed for another.
- **R10 (constraint):** The generated manifest's profile, and so the flags, the behaviour and the speed of the built program, shall not change.
- **R11 (event):** When a program's first successful build in the shared cache ends, the private `target/` its earlier builds left in its staging folder shall be removed, and the log shall say how much was freed.
- **R12 (ubiquitous):** The IDE's Build, `rcrun build` and the project tools' `build` shall all use the cache, in the folder spec 100's setting names.
- **R13 (ubiquitous):** The Build Folder dialog and the Developer's Guide shall say what the cache is, that deleting it is safe and costs one slow build, and that a new build folder starts without it; the words shall exist in the six languages.

- **R14 (state):** While the shared cache cannot be used — it cannot be created or written, or the platform's freshness in it cannot be established — a build shall behave as it does today, in its own folder, and say so in the log; the cache can make a build faster, never make it fail.

## 4. Acceptance criteria
- [x] **AC1 (R1, R2)** — in a fresh build folder two different console programs are built one after the other; the second compiles only itself. Real builds; the compiled-crate count of each is printed. *`programs_share_one_cache_and_an_old_private_target_goes`: first program 209 crates in 27.5 s, the second 1 crate (itself) in 1.8 s.*
- [x] **AC2 (R2)** — an unchanged program recompiles nothing (`an_unchanged_program_recompiles_nothing` still passes). *The same test (the first again: 0) and `an_unchanged_program_recompiles_nothing` (build 2: 0 crates, 1.4 s).*
- [x] **AC3 (R3)** — with a throwaway copy of the SDK (`stage_sdk`), one changed line in a platform crate recompiles that crate, its dependants and the program, and no third-party crate; deleting the cache folder makes the next build a cold one that succeeds. *`a_stale_platform_crate_forces_a_full_build`: a newer edit to `cobolt-lexer` compiled 8 crates (it, six dependants, the program) and no third-party one; after the cache folder was deleted the next build was cold, 209 crates, and succeeded.*
- [x] **AC4 (R4)** — a new program's staged `Cargo.lock` holds the SDK lock's version of every third-party crate it uses; a lock that pins a version the machine cannot supply is dropped and the build still succeeds offline. *The sharing test: 0 registry versions in a new program's lock that the SDK's lock lacks. `the_cache_never_makes_a_build_fail`: a lock pinning `flate2` 1.0.28 (never downloaded) is dropped, the log says so, the build succeeds.*
- [x] **AC5 (R5, R6)** — a full build of a warm program compiles the platform crates and the program and no third-party crate; a platform source changed to content with a modification time *older* than the last compile is still compiled again; a platform crate edited with a newer file time is rebuilt by cargo alone, with no forced full build. *The stale test: an explicit full build of a warm program compiled 9 crates, all platform or the program; the edit that looked a day old was compiled again; the newer edit was not a forced full build.*
- [x] **AC6 (R7)** — no code path deletes inside the cache (read and grepped); two builds of two programs started together both finish, both binaries exist, and neither log holds "No such file". *Read: the only deletions this change adds are the program's own staging files (`Cargo.lock`, the old `target/` through `discard_dir`); nothing deletes inside `shared-target` but `cargo clean`. The safety test: two builds started together on a cold cache both finished (209 and 1 crates) and both programs ran.*
- [x] **AC7 (R8)** — the log line appears when a build waits; proved on a line captured from cargo's own waiting message while another build held the cache. *`the_lock_wait_line_of_cargo_1_95_is_recognised` on the line captured from cargo; and in the two-at-once build both logs held the waiting line.*
- [x] **AC8 (R9, R11)** — after program B builds, program A's installed binary is byte-identical to before; a program with a private `target/` loses it after its first shared build and the log gives the bytes freed. *The sharing test: program A's binary was byte-identical after B's build; B's planted 1 MiB `target/` was gone and the log said so.*
- [x] **AC9 (R10)** — the generated `Cargo.toml` differs from today's only in what R4 needs (nothing in `[profile]`). *`generate_cargo_toml` and `base_dependency_block` are untouched by this change (the diff holds neither name nor a `[profile]`); the seed goes in `Cargo.lock`.*
- [x] **AC10 (R12)** — `build_single_file`, the project build and `rcrun build` reach the cache through `build_core` (read), and one test goes through `build_single_file`. *Read: the IDE, `rcrun build` and the project tools call `build_project`/`build_single_file`, which call `build_core`. The tests go through `build_single_file`; the measurement through `build_project`.*
- [x] **AC11 (R13)** — `every_text_exists_in_six_languages` and `no_english_word_reaches_a_widget…` pass; the Guide's "Where your builds are kept" says it. *`every_text_exists_in_six_languages` and `no_english_word_reaches_a_widget…` pass; the Guide's two sections and the `rcrun` note say it. The dialog on screen is the operator's to look at.*
- [x] **AC14 (R15)** — a platform source changed to different content with a file time older than the cache's record makes the next build a full one (the build reports it, the log names the crate), the stale crate and the other platform crates in the program's graph are compiled again, and no third-party crate is; with every platform source unchanged, no build is forced to be full. *The stale test: the edit looking a day old gave `forced_full = ["cobolt-lexer"]`, a log line naming it, 9 crates compiled and no third-party one; the unchanged and settled builds forced nothing.*
- [x] **AC13 (R14)** — with the cache folder made unusable (a plain file where its folder should be), the build succeeds in its own folder, as today, and the log says why. *The safety test: with a plain file where `shared-target` should be, the build used its own folder (209 crates), succeeded, and the log said the cache is not used.*
- [x] **AC12 (measured, not asserted)** — a cold forms program, then a second forms program on the warm cache: wall-clock, crates compiled and bytes on disk of each, before and after this spec, reported as numbers (GOLDEN RULE #7). *Run by hand, release profile: PowerDemo3 cold 511 crates / 163.2 s; PowerSpatial after it 100 crates / 84.1 s against 363 crates / 122.1 s in its own folder; full build on the warm cache 12 crates / 40.9 s; nothing changed 0 / 1.8 s; shared cache 1.8 GB for both, PowerSpatial's own folder 1.0 GB; the freshness check 716 ms in an unoptimised test build. In the CHANGELOG.*

## 5. Constraints & steering check
- **i18n ×6:** the dialog's added words (`ide_text_data.rs`). **Generated code:** the staged `Cargo.toml` and `main.rs` are unchanged apart from R4. **Docs:** the English Guide only; no translation of the Guide exists to delete. **System KB:** no control, property, method or event changes (the plan confirms by grep). **Fix vs feature:** a fix (operator, 2026-10-15), on `fixes`; `z` bump and a CHANGELOG entry. **Windows/Linux:** the plan must say how they are covered, as only macOS ran here.
- **Alternatives rejected:** a cache per PowerRustCOBOL version (third-party crates recompiled every release); `sccache` as the first step (an external tool; kept as the later step above); shipped `.rlib` files (toolchain-bound).

## 6. Open questions (each taken at the answer assumed here)
- **Q1 — feature or fix?** **Settled: a fix** (operator, 2026-10-15), by the 2026-08-29 precedent that what withdraws a cost without offering a capability is one. It goes on `fixes`.
- **Q2 — where.** *Assumed:* a folder named for what it holds, directly in the build folder, so spec 100's setting moves it.
- **Q3 — seeding the lock (R4).** *Assumed:* from the SDK's `Cargo.lock`, only for a program with no lock. The plan must prove that cargo accepts that lock offline when the registry cache lacks a pinned version, and falls back as R4 says.
- **Q4 — the old private `target/` (R11).** **Settled: yes** (operator, 2026-10-15), removed automatically after the first good shared build. It is a cache we created and each is 1.4–2.6 GB; spec 100's "do not touch the old folder" was about a folder the developer chose.
- **Q5 — growth.** *Assumed:* no pruning and no button now; the folder may be deleted by hand (R13). Old toolchains and feature variants stay until it is.
- **Q6 — R6's key.** *Assumed:* a content hash per platform crate (its files plus the root manifest) — not the PowerRustCOBOL version, which changes on every `z` bump even when no platform crate did.
- **Q8 — "a full rebuild" (R15).** *Assumed:* the full build of R5 — the platform crates and the program are compiled again from source and the third-party crates stay cached. Wiping the third-party crates too would put back the cost this spec removes on every stale upgrade; say so if that is what was meant.
- **Q7 — builds taking turns.** *Assumed:* acceptable. Cargo locks the cache, so two builds at once run one after the other.

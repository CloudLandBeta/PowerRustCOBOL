# Spec — The WebAssembly build target (Leptos + Tauri 2) and the host page

- **Status:** draft (needs `/clarify`). **The execution model is decided** (operator, 2026-10-19): the compiler generates WebAssembly directly, with no interpreter and no runtime in the browser — see WASM-010.
- **Folder:** specs/WASM-002-wasm-build-target-and-host-page/
- **Author:** Anthropic Claude Codex Agent   **Date:** 2026-10-19
- **Branch:** `features-2x` (version line 2.x.x). Part of the WASM series, see `specs/WASM-INDEX.md`.
- **Origin:** operator item **2** (version 2.0 generates WebAssembly; HTML, CSS3 and JavaScript load the application inside a
  pre-existing layout or fill the window's available area) and the stack named in item **1** (Tauri 2 + Leptos).
- **Depends on:** WASM-001 (the project kinds), WASM-010 (the generated program module), WASM-016 (the prebuilt player). **Amends:** spec 041 R17/R18 (*build for the host triple only*) — for the web and
  mobile kinds only; spec 017 (*one renderer everywhere*) — the web kinds are rendered by the DOM, see WASM-004.
- **Prior art:** spec 006 (removed 2026-10-14, `git show ccfa3449^:specs/006-web-wasm-projects/spec.md`): an eframe-web
  `<canvas>` bundle with `trunk`, COBOL transpiled to Rust, no interpreter shipped. Carried over: the portable-subset check
  (R3), toolchain detection (R6), no in-IDE web debugger. Changed: DOM + CSS instead of a canvas, and no Rust step either — the compiler emits the module itself (WASM-010).

## 1. Overview

Version 2.x.x builds a Web or Mobile project to **WebAssembly** instead of a native executable. A built application is **two
WebAssembly files** (operator, 2026-10-19): the **program module**, the COBOL generated by the compiler (WASM-010), and the **player**,
a **prebuilt Leptos** form engine shipped with the IDE that draws any form as ordinary DOM elements (WASM-016) — so HTML and CSS3 are the
real surface and the browser does the text, accessibility and layout work. The bundle is a set of static files (an HTML page, the two
`.wasm` files, a small JavaScript loader, the form descriptions, a stylesheet and assets) that any web server can host. **A Web build is
"emit the module, copy the player, write the page"** — no Rust toolchain on the developer's machine. For **Android and iOS** the same
frontend runs inside a **Tauri 2** shell, which supplies the native wrapper, the system web view and the store package.

A **host page** is the thin HTML/CSS3/JavaScript layer that loads the module. It supports two ways to place the application:
**in the available window area** (the application is the page), or **inside a pre-existing layout** (an element on someone
else's page).

**What runs in the browser (operator, 2026-10-19).** There is **no runtime in the browser**. The program's COBOL is compiled to a WebAssembly module that is **self-contained** — it carries the routines it needs and imports only a small host
API (WASM-010). The browser module has no `redb`, no disk and no `std::fs`; the page uses **threads** (Rayon in the player and the graphics objects, the program module in a Worker) when it is cross-origin isolated and works without them when it is not (WASM-017 R19, R20). The **backend keeps the current runtime** with all of them (WASM-003). Everything a browser program needs from disks or databases goes through the backend
(WASM-005).

**Two application styles** (WASM-011): **SPA** is the default — one page, forms loaded into the application shell — and **standalone forms**, as on the desktop, where opening a form opens it in a page or window of its own. The host page and the
bundle layout serve both.

### What exists today (checked 2026-10-19, `main` at 1.91.217)

- **The compiler is native and host-only.** `build_project` (`crates/cobolt-compiler/src/lib.rs:1737`) serialises the AST with
  bincode + gzip (`:2259-2261`), embeds it with `include_bytes!` (`:4510`), generates a Cargo project and runs
  `cargo build --release` with **no `--target`** (`:2852-2882`); the output goes to `bin/` (`:3003-3014`). The generated crate
  depends on `cobolt-form-host` and eframe 0.36 (`:3791-3799`). `BuildOptions.target` (`:1633-1639`) is only compared with the host
  triple; any other value is `UnsupportedTarget` (`:752`, `:1993-2000`), by design (spec 041 R17/R18).
- **There is no WebAssembly anything.** No `wasm-bindgen`, `web-sys`, `js-sys`, `leptos`, `trunk` or `tauri` in any `Cargo.toml` of the
  workspace (they appear in `Cargo.lock` only transitively); the only `wasm32` mention is a `cfg` gate on `syntect`
  (`cobolt-ide/Cargo.toml:127`). `toolchain.rs` only checks the rustc version and offers the rustup installer.
- **There is no COBOL → Rust generator.** `cobolt-codegen` turns *forms* into COBOL; the only Rust the compiler emits from COBOL
  source is `EXEC RUST` blocks (`cobolt-compiler/src/exec_rust.rs`). The program runs in the **tree-walking interpreter** bundled
  into the binary.
- **The runtime is not browser-ready — and, by the operator's decision, it will not go to the browser.** The event loop blocks on
  `std::sync::mpsc` (`cobolt-runtime/src/interpreter.rs` ~`:3942`, `:3958`); `thread::spawn` appears in 12 runtime files
  (`async_op.rs` among them); `std::fs` in 23 (`interpreter.rs` 62 times, `indexed_disk.rs` 201); `Instant::now` 23 times in
  `interpreter.rs`; `redb`, `sysinfo`, `aes-gcm`, `getrandom` and `chrono` (clock) are linked whatever the features. All of that stays
  where it is: it is the **backend's** runtime. The browser module is generated (WASM-010) and takes none of it. The lexer, AST, parser and
  semantic crates use no file, thread, process or network API (the lexer reads files only in `copybook.rs`), which is what lets the
  compiler front end feed the generator unchanged. `cobolt-forms` without `render` is free of egui but has unconditional `lopdf`,
  `mermaid-rs-renderer` and `tl` dependencies and ungated `std::fs` in `viewer.rs`, `dropzone.rs`, `assets.rs` and `items_file.rs`;
  `cobolt-form-host` is native (`rfd`, `pollster`, eframe). The player that draws the forms in the browser (WASM-016) is therefore new code, not a
  port of these.
- **A WebAssembly emitter is not in the workspace's own dependencies:** `wasm-encoder` and `wasmparser` are in `Cargo.lock` only
  transitively; no engine (`wasmtime`, `wasmi`) is (WASM-010 Q2).
- **Optional bridges are already feature-gated** in `cobolt-runtime`: `default = sql, http, maps, kb, smb, pdf, office, aws, images,
  audio`, and generated applications use `default-features = false` (`cobolt-compiler/src/lib.rs:3770`); that mechanism serves the
  desktop and backend profiles, not the browser.
- **Docs and specs that already speak of the web:** the CLAUDE.md 2.x.x section; `CONVENTIONS.md` and spec 047 mention WebAssembly.

## 2. Goals / Non-goals

- **Goals:**
  - A **Build** for the Web kind that produces a static bundle, and for the Mobile kind an Android package and an iOS package.
  - The **same program behaviour** in the browser as on the desktop for everything the portable subset allows.
  - A **portable-subset check** at Check/Build that says, per line, what cannot run in a browser and what to use instead.
  - The **host page**: window-filling mode and embedded-in-a-layout mode, with a small documented JavaScript surface.
  - Toolchain detection with clear, honest messages.
- **Non-goals:**
  - A runtime, interpreter or the `redb`/disk/thread support in the browser (the operator, 2026-10-19: the backend keeps them).
  - Server-side rendering, offline/PWA behaviour, hosting or deploying the bundle (WASM-INDEX lists
    each as a proposed spec).
  - A web debugger inside the IDE (browser developer tools serve; source maps where the toolchain gives them).
  - Changing the desktop build (egui, `bin/`, host triple) in any way.
  - The backend (WASM-003); it is a different binary.

## 3. User stories

- As a developer, I want **Build** on a Web project to give me a folder I can drop on any static host, so that deployment needs
  nothing from me but a web server.
- As a web developer with an existing site, I want to **place the application inside one element** of my page, so that my header,
  navigation and footer stay mine.
- As a developer, I want the IDE to tell me **which line** uses something a browser cannot do, so that I fix it before building.
- As a mobile developer, I want the same project to give me an **Android** and an **iOS** package, so that I keep one codebase.

## 4. Requirements (EARS)

**The build**
- **R1 (event):** When the developer builds a Web project, the IDE shall produce, in the project's build folder (specs 100/101 govern
  the folder and cache), a **static bundle**: the host `index.html`, the WebAssembly **program module generated from the program's COBOL — one for the whole project, in a multi-memory and a single-memory variant** (WASM-010, WASM-017 R1, R9), the **prebuilt player** (in a plain and a threaded variant, WASM-016) that draws the forms (WASM-016, copied, never compiled), the JavaScript loader, the form descriptions, the form stylesheet (WASM-007) and the assets the forms use,
  with content-hashed file names; for the standalone application style (WASM-011) the bundle shall give each standalone form its own entry page.
- **R2 (event):** When the developer builds a Mobile project, the IDE shall produce an **Android package** and/or an **iOS
  package** that wrap the same frontend in a Tauri 2 shell, for the platform(s) the project selected.
- **R3 (event):** When the developer runs Check or Build on a Web or Mobile project, the IDE shall validate the COBOL against the
  **portable subset** and report each construct that cannot run in a browser as an **error** at its line, naming the construct and
  the alternative (a remote call, WASM-005, or a different control); no bundle shall be produced while such errors remain. Constructs
  that need the local disk (any file organisation on disk, the disk indexed engines and `redb` included), a child process, an OS thread, a native
  socket, SQL, `EXEC RUST` or an embedded secret are not portable; INDEXED files declared `STORAGE IS MEMORY` and `SORT`/`MERGE` held in
  memory are portable (WASM-010 R7, Q8). The generator is where the others are refused (WASM-010 R8).
- **R4 (ubiquitous):** For every construct in the portable subset the application shall behave as the same program does on the desktop
  runtime: same results, same `ON SIZE ERROR`/`ON EXCEPTION` outcomes, same event order. Any difference shall be listed, per construct,
  in one place the developer can read, and the equality is **measured** as WASM-010 R16 says.
- **R5 (ubiquitous):** The user interface of a Web or Mobile application shall be built as DOM elements styled with CSS3 (not drawn on
  a `<canvas>`), so that the browser's text selection, zoom, accessibility tree and find-in-page work. The one exception is the **drawing controls of class B** (charts, maps, gauges and the like, WASM-004 R4), which may use SVG or a `<canvas>`
  *inside their own element*; the form, its layout and every ordinary control remain DOM.
- **R6 (event):** When a required tool is missing, the IDE shall name it, say whether it can install it itself, and install only what is
  safe to install after the developer agrees (`rustup target add` is; Xcode and the Android SDK are not). A **Web** build
  needs **no tool of the Rust toolchain**: the compiler emits the module itself (WASM-010 R1) and the player is prebuilt (WASM-016 R1); the
  `wasm32` target and the bundler are needed only by the product's own build, which produces the player. A **Mobile** build always needs
  the Tauri 2 CLI, the Android SDK/NDK and Xcode (WASM-012 R2) and compiles a shell per application, so it also needs the Rust toolchain.
- **R7 (ubiquitous):** The bundle shall contain **no secret**: no key, token, password, connection string or client secret; Build shall
  scan the produced files and the forms for them and fail, naming the file and the pattern (the credential gate the examples already need).
- **R8 (ubiquitous):** Build shall report the size of each part (module, loader, stylesheet, assets) so that growth is visible from
  one build to the next.
- **R9 (constraint):** A Desktop project shall build exactly as before; nothing in this spec changes `bin/`, eframe or the host-triple rule
  for the desktop kind.

**The host page**
- **R10 (optional):** Where the application is placed **in the available window area**, the page shall make it fill the viewport (including
  the dynamic viewport on phones) without producing scroll bars of its own, and shall re-lay it out when the window changes.
- **R11 (optional):** Where the application is placed **inside a pre-existing layout**, the page shall mount it into an element chosen by the
  host (an attribute or a selector), size it to that element, and re-lay it out when the element changes size (not only when the window
  does); the responsive breakpoints of the forms shall be evaluated against the **element's** width in this mode.
- **R12 (optional):** Where the application is embedded, the host page's CSS shall not leak into it and the application's CSS shall not leak
  out, while the host can still pass theme values (CSS custom properties) in.
- **R13 (ubiquitous):** The JavaScript surface the host can use shall be small and documented: mount, unmount, initial parameters
  (locale, theme, backend address), and events out (ready, error, navigated, signed in/out). It shall offer no way to evaluate arbitrary
  script.
- **R14 (ubiquitous):** The application shall run under a Content-Security-Policy that allows WebAssembly (`'wasm-unsafe-eval'`) but not
  `'unsafe-eval'`, and the build shall print the policy it needs (script, style, font, image and connect sources).
- **R15 (state):** While the module is loading, the page shall show progress; if the browser cannot run WebAssembly, or loading fails, it
  shall show a readable message and a way to retry, not a blank page.
- **R16 (ubiquitous):** Each program module in the bundle shall be a **self-contained** module of WASM-010 R1–R2: it carries what it needs to run, imports
  only the host API, and the bundle shall contain no interpreter, no AST and no runtime library for it.
- **R17 (ubiquitous):** The host page shall serve both application styles of WASM-011: for **SPA**, one entry page and a router; for **standalone
  forms**, one entry page per form, each instantiating the module of its own form. The embedded mode (R11) supports SPA; whether it
  supports standalone forms is WASM-011's decision.
- **R18 (ubiquitous):** The Build shall declare a **baseline set of WebAssembly features** and a **matrix of supported browsers** (Chrome and Edge, Firefox, Safari, the iOS web view, the Android WebView), and the loader shall probe the browser against it and show the readable message of R15 below the baseline; the player and the program
  modules shall be built in the variants of WASM-017 R9 and R19: the program module **multi-memory by default** and a **single-memory variant** (always for iOS, and for any matrix that includes Safari, where the Web bundle carries both and the loader probes), the player **threaded** and **plain**; the baseline is what the single-memory module and the plain player use, and a feature above it
  is chosen by probe (WASM-017 R18).
- **R19 (ubiquitous):** The loader shall fetch the program module with `fetch` and **streaming instantiation** (ES-module integration only if feature-detected, WASM-017 R3), fetch the player's heavy parts on first use, create a form's data region when the form is created and release it when it is destroyed (WASM-017 R2–R5), and choose the program-module variant, the player variant and the execution
  mode (Worker or main thread) by probing the browser (WASM-017 R18, R19).
- **R20 (ubiquitous):** **Threads are used when the page is cross-origin isolated** and the application works without them when it is not. The Build shall generate, for each documented static host and for the standalone server the IDE can start, the headers `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy` (`require-corp` or `credentialless`) and print them with the trade-off that resources from other origins must then allow it;
  it may also offer a service-worker shim that sets them for hosts that cannot (off by default). In the **embedded mode** (R11) the application is isolated only if the host page is, and otherwise starts on the plain player and the main thread (WASM-017 R19).

## 5. Acceptance criteria

- [ ] **AC1** — A hello-world Web project builds to a folder of static files that, served by any static server, shows its form and answers a
  button click in a headless browser.
- [ ] **AC2** — The same hello-world, mounted into one `<div>` of a test page next to other content, fills only that `<div>`, resizes with it,
  and neither page's CSS affects the other (a test asserts a computed style on each side).
- [ ] **AC3** — A form using a construct outside the subset (for example an `OPEN` of a disk file) makes Check fail with the line, the
  construct and the alternative; no bundle is written.
- [ ] **AC4** — A program in the subset, run on the desktop runtime and as the generated module (headless), prints identical output for a fixed set of
  programs; the conformance list and its numbers are WASM-010 R16 and AC7–AC8, which is what R4's "behave as" is measured against.
- [ ] **AC4b** — The built bundle contains no interpreter, AST or runtime library, and the program module's import section lists only the host API (R16).
- [ ] **AC5** — A key placed in a form's property (a deliberate test secret) stops Build with a message that names the file and pattern.
- [ ] **AC6** — Missing-tool messages for each tool of R6 appear when that tool is absent (tested by hiding it from `PATH`).
- [ ] **AC7** — The Mobile build produces an Android package and (on macOS) an iOS package from the same project; both start and show the form.
- [ ] **AC8** — A Desktop project builds byte-for-byte as before (the existing compiler tests stay green).

## 6. Constraints & steering check

- **The frontend↔backend channel (WASM-INDEX D21, operator 2026-10-24):** whatever this spec puts on the channel between the frontend and the backend obeys the series-wide ruling — the channel is asymmetrically encrypted with a key pair generated when the application starts; a broken connection is retried with a timeout of 10 s, raised by 10 s on each retry, for at most 3 cycles, then an exception is raised; while the frontend retries, all mouse and keyboard input is blocked and the "connecting" modal of WASM-016 R20 (WASM-012 R15 on a device) is shown, appearing when the connection breaks and disappearing when it is re-established. The ruling is owned by WASM-003 R24–R26, WASM-016 R20–R21, WASM-012 R15, WASM-005 R18, WASM-014 R18 and WASM-013 R17; this spec adds nothing of its own to it and must not contradict it.
- **i18n (6 languages):** yes — toolchain messages, the portability diagnostics and the Build report are IDE strings.
- **Generated-code contract:** the generated COBOL and its banner are unchanged; the web frontend is a *new build artefact* downstream of
  the generated `.cbl`, never hand-edited. Spec 017's "one renderer" is amended for the web kinds (the DOM is their renderer; WASM-004).
- **Docs:** `docs/` is not touched on 2.x.x (CLAUDE.md ruling); the guide chapter is planned in WASM-INDEX.
- **System KB:** a build target is not a control/property/event; the portable-subset list is, however, something Grace and the agents must
  know — it is part of the documentation/KB spec in WASM-INDEX.
- **Fix vs feature:** **feature** (`features-2x`).
- **Tech steering:** *no external COBOL toolchain at runtime* still holds; the new dependencies (WebAssembly target, bundler, Tauri CLI,
  platform SDKs) are **build-time** only. MSRV 1.92 applies to every crate added; the crate probe belongs to `/plan`.

## 7. Open questions

- **Q1 — The execution model — decided.** The operator ruled on 2026-10-19: the compiler **generates WebAssembly**; there is no interpreter or
  runtime in the browser; the final code carries what it needs; `redb` and disk are not in the browser (threads are, since 2026-10-20: WASM-017 R19); the backend keeps the current
  runtime. WASM-010 specifies it. Still to confirm there: that the generator emits the module **directly** rather than through Rust (WASM-010 Q1).
- **Q2 — Bundler and framework layout:** Leptos in client-side-rendering mode with `trunk`, or `cargo-leptos`? Recommended: client-side
  rendering with `trunk` (a static bundle, no server component).
  **Decided (operator, 2026-10-22):** Leptos with `cargo-leptos`. The server runs the developer's COBOL programs; its Leptos plumbing is invisible to the developer, who writes and sees only COBOL (WASM-003 R2).
- **Q3 — Is Tauri 2 also used for the desktop kind** later (one web frontend for all), or does Desktop stay on egui? Recommended: Desktop stays
  on egui in 2.0 (R9).
  **Decided (operator, 2026-10-22):** Desktop stays on egui.
- **Q4 — `EXEC RUST` in a web project — decided by the model:** rejected (a generated module has no Rust step), allowed later only through a
  backend program or a future external-crates spec (WASM-INDEX).
- **Q5 — A size/startup budget** for the module and a measured target for first paint: set at `/clarify` once phase A of WASM-010 is measured.
  **Answered (operator, 2026-10-22), to confirm:** a budget of 5 MB. *Whether it caps the first download (module, player, loader) and which first-paint target applies are still to state.*
- **Q6 — Where the host page's JavaScript comes from:** hand-written and shipped as a fixed file (recommended; small, auditable), or generated
  per build.
  **Decided (operator, 2026-10-22):** generated by the IDE at every Build and never edited by hand, like every generated artefact (WASM-013 R9).
- **Q7 — The player — decided.** The operator ruled on 2026-10-19: **two `.wasm` files** — a **prebuilt Leptos player** that draws any form, plus the generated COBOL
  module; a Web build is *emit the module, copy the player, write the page*, with no Rust toolchain. The player has its own spec, WASM-016. The cost, accepted: no
  per-project Leptos code, so no developer-written components and no `Custom` plug-in controls on the web in v1.

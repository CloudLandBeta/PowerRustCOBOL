## 2. The two fixes in the tree

### 2.1 Black triangles in panel corners after visiting another form

**Report:** first load is clean; visit a form with a different style, come back,
and black triangles sit in the corners of many panels — permanently.

**Root cause — a colour bug, not a geometry bug.** The corner-notch mask repaints
"what is behind" over a rounded container's corners, and took that colour from the
ambient `ui.visuals().panel_fill`:

* The shell hosts its root form in the ContentPane (`Surface::Pane`), where the
  **pane** paints the backdrop and the engine is handed a deliberately
  *transparent* one so nothing paints twice. Compositing a zero-alpha colour over
  the ambient fill returns the ambient fill unchanged — so in pane mode that
  ambient value was **100 %** of the notch colour.
* A self-contained theme (Elegance) writes its palette into the **shared**
  Context's global style: `install_widget_visuals` → `Theme::install` →
  `ctx.global_style_mut`, setting `panel_fill = #0F172A`. `LiquidGlassTheme`'s
  `install_widget_visuals` is the trait-default **no-op**, so nothing ever puts it
  back. `#0F172A` is `Palette::slate().bg` — literally the navy in the operator's
  Customers screenshot and literally the colour of the triangles.

Only "some corners" because the notch guardian masks only corners a child
overlaps. Clean on first load, black forever after one visit.

**Fix.** The caller states what it painted: `Backdrop::behind_fill: Option<Color32>`
(`render.rs`), set from the pane's own `painted.bg` in `host.rs`. Ambient survives
only as the fallback for the designer canvas, which genuinely does own its
visuals. Pinned by `render::notch_ambient_tests` — renders the same scene under
two ambient fills; the notch was `#f0f0f0` vs `#0f172a`, now `#eaebef` both times.

**Left alone deliberately.** The theme-install asymmetry itself. `Theme::install`
early-returns on a private ctx cache (`Id::new("elegance::theme")`), so restoring
a baseline would leave the *next* Elegance form un-themed. Two ambient reads
remain in the paint path and are theoretically leaky the same way, with no report
against them: `render.rs:4177` (`strong_text_color`) and `render.rs:4883`
(list selection fill).

### 2.2 Controls past the form edge never rendered

**Report:** a control placed beyond the designed form width — visible and
selectable on the canvas — never appears at run time; maximizing the window
reveals only more background.

**Root cause.** Every control was clipped to the **designed** form rect, so
anything beyond it was clipped out of existence regardless of window size.

**Fix.** The designed rect is now the floor, not the ceiling — the clip is the
designed rect unioned with the room actually available. Nothing is stretched or
re-laid-out; the window's own edge is still the only thing that cuts a control,
and a child is still clipped to its Panel/GroupBox. Pinned by
`render::beyond_the_form_edge_tests` (two tests: the control paints; the child is
still clipped).

⚠️ **Known limit, documented:** a window *smaller* than the form scrolls the
form, but will not scroll out to a control beyond the designed edge — the
scrollable area is still the designed rectangle.

## 3. Spec 053 — code locations and search

`specs/053-code-locations-and-search/` — `spec.md` (R1–R36, AC1–AC19), `plan.md`,
`tasks.md` (T1–T31). **Nothing implemented.** Next step is `/implement`.

**What it is.** Two operator asks that turned out to be one missing concept:
precise error locations (`Form ▸ Site`, clickable) and a project-wide code search.
Both are blocked on there being no *address* for "a place a developer writes
COBOL". There are **nine** such places, enumerated from the model, not the
request: control event handler, form lifecycle handler, user procedure, the five
structure sections (`SPECIAL-NAMES` / `REPOSITORY` / `FILE-CONTROL` /
`FILE SECTION` / `WORKING-STORAGE`), and Common Code files.

**What the design turns on.** Codegen already ships a partial source map —
`generate_with_user_lines` returns the line ranges of developer-authored handler
and procedure bodies, built for the debugger. Right seam, wrong payload: a range
says *that* a line is user code, not whose or which line of theirs, and it is
blind to the structure sections (they have no `PROGRAM-ID`). The plan widens the
payload rather than adding a parallel API, so every existing consumer keeps
working and the generated bytes cannot move.

**Two guards must land before the things they guard** — this is the single most
important sequencing point in `tasks.md`:

* **T2** — generated `.cbl` is byte-identical — **before** any codegen writer is
  touched (T5–T8).
* **T18** — the search window holds its size across 120 frames — **before** the
  window has any content. "Make it resizable" is a twice-burned failure here:
  egui ≥0.35 `Resize` does `desired_size.max(measured_content_min)` every frame,
  and a search window's body is a long result list. The cure is the existing
  `error_modal_scaffold` shape plus an interior partitioned by embedded panels
  with no estimated heights.

**Split point.** If the operator classes the diagnostics half as a **fix**, the
cut is at **T17** with no redesign: T1–T17 → `fix/code-locations` (f=97),
T18–T26 → `feat/code-search` (f=96, prefix `[Noticia]`). Each half is
independently green.

## 7. Follow-ups worth a spec of their own

* **Two syntax validators disagree.** `validate_handler_syntax`
  (`designer.rs:1413`) parses a handler *in isolation* under a 2-line scaffold and
  reports handler-relative lines; the Output path parses the *woven* program. The
  same broken code can produce different messages in the two places. Spec 053
  names the woven check as authoritative and keeps the modal's fast local
  feedback — **do not "tidy up" by deleting either** without deciding this.
* **Runtime error locations.** Explicitly deferred; `SourceMap` derives serde so
  it can ship into a compiled binary without a retrofit.
* **The theme-install asymmetry** (§2.1) — a self-contained theme mutating the
  shared global style with no counterpart. Corner painting no longer depends on
  it; anything else that reads ambient visuals still does.
